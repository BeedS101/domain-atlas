# Domain Atlas Protocol — Specification

**Status:** Draft v1.41 (informational, pre-standardization)
**Date:** 2026-10-03
**Author:** Bruno da Silva

A decision on an open license is still under review.

**A note on names.** "Domain Atlas" and the `atlas` prefix used throughout (`atlas.wearable`, `/.well-known/atlas-key.json`, `domain-atlas/1.0`) are working names, not a settled brand — that decision is still open. The technical prefix is deliberately kept separate from whatever the project ends up publicly called, the way `ipfs://` outlived a dozen rebrands of the company behind it. Renaming the project later costs nothing here; only renaming the wire-level prefix would.

Separately, nothing in this document requires any of the specific names the reference implementation's own demo content happens to use — domain names, world names, or individual asset classes like `atlas.wearable.ring` are illustration, not a naming scheme a real deployment has to follow. §5.1's two-tier convention (a small `atlas.*` vocabulary worth standardizing, reverse-domain keys for everything a deployment invents on its own) is the only naming rule this spec actually sets; a real domain names its own domains, worlds, and classes however it likes.

**Revision history.** v0.1 through v0.5 were built incrementally, each round closing one open question. v1.0 consolidated all of it into one document and applied a terminology pass (`rules` → `policy`, `category` → `profile`, `worldType` → `scale`, `allowItemDrops` → `itemDropsAllowed`). v1.1 adds the piece needed for scarcity to mean something economically rather than just cryptographically: fungible resources (§5.4) and a live cross-domain exchange mechanism (§7), aimed at letting many independently-run worlds that agree on the same resource vocabulary function as one coherent economy without any of them being in charge of it. v1.2 adds per-page discovery and anchors (§3.5) — a single page can now point straight at its own space or a specific location inside the domain's larger one, instead of every visitor landing at one shared front door. v1.3 adds one security consideration (§9) flagging the regulatory exposure of bridging real-money payments into a resource that's tradeable across domains — no schema change, just an honest warning where a domain owner would look for one. v1.4 closes a gap every prior version had without saying so: §5.2's transfer-on-loss and §7's trade intent were both specified in prose only, with no actual credential shape, and neither one works without an answer to a harder question this spec had also never addressed — how a visitor's WebAuthn passkey signs a specific application payload at all, as distinct from the simpler bare-possession proof (a fresh assertion over a random, disposable challenge) that §6 step 4 and §5 step 3 already relied on and still do. §6.2 specifies that payload-signing mechanism, and §5.2 and §7 now each give the concrete, canonical credential shape their prose already implied, built on it. No behavior described in v1.0–v1.3 changes; this is filling in wire formats a working implementation needed and found, not revising anything decided earlier. v1.5 adds a second, deliberately lower-trust way for a world to exist at all: a **key-anchored world** (§3.6), whose identity is its own signature and public key instead of a domain, for anyone who wants to publish a space without owning one. Nothing about credential verification (§5) or identity (§6) needed to change to allow this — both were already trusted by signature, not by address — only the manifest and portal shapes needed a second option. What's new is mostly the honesty required around it: an explicit client obligation (§3.6.1) to warn hard, every time, before treating a key-anchored world as anything close to a domain's guarantee, plus a third, orthogonal warning for plain HTTP — which, worked through carefully, turns out to hurt a domain-anchored world worse than a key-anchored one, not the other way around. v1.6 lets a domain-anchored world optionally borrow the same signature this version just gave key-anchored worlds, for a reason that has nothing to do with first-contact trust — TLS and DNS already own that job — and everything to do with a domain a visitor's *already seen before*: a persistent, self-signed identity a returning client can notice change even when the certificate and DNS both still check out fine, which is exactly the blind spot §9's domain-takeover bullet already admitted this spec had. §3.7 defines it, strictly optional on both ends and explicitly not a hard lock — the browser world tried a stricter version of this once (HTTP Public Key Pinning) and walked it back after it locked sites out of their own trust, so this reuses §5.3's rotation-history approach instead of a single forever-fixed key. v1.7 makes explicit something the schema already quietly allowed but the prose never actually said: `atlas-key.json` (§5.3) isn't limited to one valid key at a time. §5.3.1 sanctions concurrent keys outright — redundancy across more than one issuing server or delegate, and separate keys for separate purposes (an issuance key need not be the same key §3.7 uses to sign a manifest) — and is explicit that this was always structurally possible, just never stated, which is exactly the kind of gap worth closing before an implementer reasonably assumes the opposite. v1.8 gives a concrete wire format to something §5.4's prose already named as a design goal without ever specifying — a resource balance being "combinable (two balances of the same class becoming one)". `supersedes` (§5.4) may now hold an array of ids, not just a single id or `null`, for the case where one new balance replaces more than one old balance at once (a consolidation) rather than exactly one (a mint's remainder, a trade settlement). Every old id in the array is revoked in the same act as before, under one new §5.3 reason code, `"consolidated"` — kept distinct from `"superseded"` so a client reading the revocation list can still tell a split/trade-remainder from a merge, the same reasoning that gave `"superseded"` its own code in the first place rather than reusing `"issuer-request"`. v1.9 retires the item/resource split itself. Every version through v1.8 treated "unique" and "fungible" as two different credential types — `domain-atlas-item/1.0` and `domain-atlas-resource/1.0` — because the schema had no field to say which one a given claim was; §5's item shape and §5.4's resource shape grew their own parallel copies of `class`, `properties`, `supersedes`, and the same four-step verification, diverging only in the one place that actually mattered (does this thing have a quantity or not) while duplicating everything else. That divergence was never load-bearing — nothing about verifying a signature, checking a revocation list, or trusting an issuer's key cares whether the thing being verified is stackable — so v1.9 collapses both into one `domain-atlas-asset/1.0` credential (§5), carrying an `asset` wrapper (item's shape) plus a top-level `quantity` (resource's field, now always present — `1` for what used to be an item) and one new signed boolean, `fungible`, that says which regime a given class lives in. Splitting, consolidating, and trading (§5.4, §5.4.1, §7) now check `asset.fungible` instead of checking which credential type showed up; the owner-signed whole-unit transfer (§5.2) and issuer-initiated reissue (§5.1.1) work the same way, gated the other direction. A second new signed field, `presentation` (`"collectible"` | `"document"`), rides alongside `fungible` for a different reason — not a behavioral gate at all, just a signed hint for which UI surface a client shows something in, since a membership card and a Bronze Compass were never really the same kind of thing to look at even once nothing about verifying them differs. Everything this version changes is the shape of the claim; §6's identity flow, §7's matching and atomicity, and every security property in §9 hold exactly as before, because none of them ever depended on which of the two old types was on the wire. v1.10 catches this document up to two mechanisms a working implementation had already built and shipped without ever formalizing here. First, §6 step 5 and §6.1 document **local-password identity**: a second, explicitly lower-assurance "self" mechanism alongside WebAuthn, for a visitor or environment without a usable authenticator — an ordinary keypair encrypted at rest under a password, with its own portable backup format (password plus a separately-generated seed phrase, combined). §6.2 is revised accordingly: `signerRole: "raw-ecdsa"`, previously scoped in prose to test-harness use only, is now a second legitimate value for a real visitor's own authority, on equal footing with `"webauthn"` provided the public key it's checked against is verified to actually belong to that visitor's registered identity — nothing about §5's credential verification or §9's security properties changes, since both already trusted a public key by signature, never by which mechanism produced it. Second, this version adds **§11, Mail** — domain-to-subscriber mail and its attached-gift variant, and Post Office user-to-user mail (symmetric membership, per-member consent settings, `handle#domain` addressing, and volume-based abuse flagging) — none of which had ever been given a protocol-level section here despite both README.md and issuer-php/README.txt citing "SPEC.md §11.3" throughout their own descriptions of it. No behavior changes in either case; this is the same kind of catch-up v1.4 already did once for §6.2's signing mechanism, writing down a wire format and a set of rules a working implementation had already settled by necessity. v1.11 names a convention this document had been quietly relying on without ever stating it: §3.4.1, **domain-level defaults, per-world overrides**. `policy.acceptedItemClasses` could already be declared once at a manifest's top level as a domain-wide default, with any world's own value winning outright when present — a working implementation had already built this, but nothing here said so, and there was no canonical rule to point a future field at instead of each one re-deriving its own shape from scratch. §3.4.1 states the rule once, generally, so it applies by default to any future per-world policy field a domain plausibly wants to set once for every world it owns, rather than being rediscovered ad hoc each time. No existing field's behavior changes. v1.12 gives `policy.identityRequired` (§3) the prose definition it had never actually gotten, despite being declared on every world in both demo manifests since early on: a visitor needs an identity (§6) before entering, checked and enforced by the client itself, since unlike `guestAccess`/`discoverable` a domain's own backend has no way to observe a visitor's wallet state before a scene loads — there is no other place this check could live. Follows §3.4.1's shape like any other per-world policy field. No other field's behavior changes. v1.13 adds two things, one small and one that fills a real gap §7 always had. First, a third signed asset-level flag, `asset.tradeScope` (§5), alongside `fungible`/`presentation` — `"bound"` for a relationship credential (a domain, Post Office, or Trading Station membership) that must never be split, consolidated, or traded regardless of how general a trading mechanism later becomes, `"local"` as the explicit name for what was already true of everything tradeable (a trade only ever finalizes at the asset's own issuing domain, a cryptographic fact, not a policy), and a reserved `"global"` value for later. Second, §7.1: remote (asynchronous) trade settlement — a visitor can now submit their own half of a trade to a station on its own, holding a new `atlas.tradingstation.membership` credential, instead of requiring both counterparties present in the same call the way §7's original mechanism still requires and still supports unchanged. Delivery to an absent counterparty once a match settles reuses §5.1.1's supersession-update channel and §11's mail-gift-attachment mechanism verbatim — no new client-side delivery mechanism was needed for either. Both changes are additive: no existing credential shape, endpoint, or trust property from v1.0–v1.12 changes behavior. v1.14 replaces §7.1's counterparty-pinned remote settlement with open, unpinned listings: a visitor posts an offer naming no counterparty at all, and any other member of that station may claim it — §7's original Match step (mirrored offer/want between two intents that each name the other) no longer describes this path. This is a real behavior change to §7.1, not an additive one, made deliberately: pinning a remote intent to a specific counterparty's public key assumed a visitor already knew who they were trading with, which is a far narrower case than an actual market, where a seller has no way to know their buyer in advance. §7's original in-person mechanism — both signed intents arriving in the same call, each naming the other — is untouched; two visitors standing at the same stall who already know each other can still trade that way, it's a different, still-valid use case that v1.14 doesn't touch. Three endpoint-level pieces carry the new model: a station now exposes its open, unexpired listings for anyone to browse (no membership required to browse — only to post or claim, the same asymmetry a Post Office's own inbox-check already has, §11.3); a claim action names a specific listing by id and settles it the same atomic way §7's Settle step always has; and a cancel action lets a poster withdraw their own still-open listing, signed the same way any other action in this spec is. Delivery to an absent poster once their listing is claimed is unchanged from v1.13 — the same supersession-update and mail-gift-attachment paths, still no new delivery mechanism needed. v1.15 removes §7's original in-person mechanism entirely — the same-call, mutually-pinned pair of intents that opened this section from v1.0 onward, superseded in practice by the open-listing model v1.14 added. Every trade now goes through what was §7.1: post, browse, claim, cancel. §7.1 no longer exists as a separate subsection; its content is folded into §7 itself, since it's now the only mechanism this spec defines, and §7's prose no longer describes itself relative to a companion section that no longer exists. Nothing about the credential shape, the Trading Station membership gate, or the atomicity/delivery guarantees changes from what v1.14 already specified for the async path — this version's only change is removing the now-redundant synchronous alternative and rewriting §7 to stand on its own. v1.16 is a documentation-only correction, no behavior or schema change: §6 step 5's reference-implementation iteration count was quietly raised from 250,000 to 600,000 (task #118) without this document ever catching up, so the prose now says 600,000; and §5's and §5.4's example asset credentials both mislabeled the issuer's public key as `"base64url-ed25519-public-key"`, a leftover from before the signing algorithm was settled — the issuer key has been ECDSA P-256 everywhere else in this document, and in every implementation, since it was first specified, so both examples now read `"base64url-ecdsa-p256-public-key"`. v1.17 adds §11.4, **domain-to-domain federation**: closes the gap §11.3's own `handle#domain` addressing left open since v1.10, where a handle's domain suffix looked like a routing instruction but a message could never actually reach anyone outside the sender's own Post Office — §11.3 step 3's "both parties belong to the *same* Post Office" was a hard requirement, not a common case. A relaying domain may now forward a message on to the recipient's own home domain instead of requiring the recipient to also hold membership at the domain being sent through, authenticated by a new attestation the relaying domain signs with the same key `.well-known/atlas-key.json` already publishes — the same cross-domain trust bootstrap §5 step 1 already relies on, no new discovery mechanism needed. §11.3 step 2 (sender membership) is unchanged and still checked first, by whichever domain the sender actually submits to; §11.3 step 3 (recipient membership and consent) is unchanged and still checked last, by whichever domain the recipient actually belongs to — federation only ever inserts a relay hop between two domains that each already do exactly what they did before. Federation is open by default (any domain publishing a valid `atlas-key.json` may relay to or receive from any other, matching this spec's existing no-registration posture for portaling between domains at all), with a conforming implementation SHOULD-level allowance for a domain to unilaterally stop accepting a specific relaying domain's attestations — a domain-local operational decision, not a negotiated federation-membership state. Trading (§7) is explicitly out of scope for this version; a cross-domain trade still has no answer for whose ledger would hold it. v1.18 adds §7's **catalog discovery** paragraph, closing a gap the section's own Posting step always had: naming a `want` requires already knowing what a station is willing to mint, and before this version a client had no way to learn that except hardcoding it. A station now exposes its own tradable fungible classes (`class`, `name`, optional `thumbnail`, `tradeScope`) for anyone to read, filtered to `fungible === true` and `tradeScope !== "bound"` — the same two conditions §7's own possession check already requires of a presented balance, applied here one step earlier, before a trade is even composed. Scoped deliberately to a station's own catalog only; fetching a foreign domain's catalog while composing a cross-domain trade is a natural extension of this same read (using `tradeScope: "global"`, reserved since v1.13) but is left unspecified, same as real cross-domain settlement itself (§9's federation note, v1.17's closing sentence). v1.19 adds §7's **currency conversion** paragraph: a domain may convert one of its own fungible classes into another of its own fungible classes directly, no counterparty or listing involved, at rates (`exchangeRate`) it declares itself per class relative to a domain-chosen base currency and surfaces through the same catalog v1.18 just added. This is explicitly a domain-set convenience, not a market — nothing here discovers a fair price the way the trading mechanism does between two independent visitors, and designating a base currency carries no special settlement authority beyond being the shared unit the rate arithmetic routes through. No existing endpoint, credential shape, or trust property changes; this is a new, self-contained mechanism alongside trading, not a modification to it. v1.20 adds §5.5, **world drops**: a visitor may leave an asset in a world for anyone present to find and pick up, with no addressee and no negotiation — the one transfer shape this spec had never covered, every prior mechanism (trade, gift, split) requiring either a specific counterparty or an open listing a claimant matches against. A drop is hosted by whichever domain's world it lands in, independent of which domain actually issued the credential; claiming it always revokes the dropped credential and mints a fresh one to the claimant (§5.3), the same real transfer-of-custody primitive trade settlement and consolidation already use, with no special case for a visitor reclaiming their own earlier drop. A concurrent double-claim is resolved by treating removal from the drop store as the reservation itself, the same "first remover wins" mechanism §7's own listings already use. Claiming a drop whose issuer differs from the hosting domain relays to the issuing domain using the identical attestation-and-verify trust model §11.4 introduced for cross-domain mail — the second use of that pattern, not a new one. `asset.tradeScope === "bound"` (§5, v1.13) is rejected outright, now enforced by the hosting domain's own server rather than left to client goodwill as §5's original wording implied. Dropping only part of a fungible balance is not a new server-side capability — a visitor splits off the exact amount first (§5.4) and drops that whole balance — so §5.5's own drop/claim mechanism never needs quantity arithmetic of its own. v1.21 adds §12, **Calendar**: a domain, and independently any of its worlds, may publish a schedule of events — a manifest-level `calendar: true` for a domain-wide calendar, and a `calendar: true` on any individual world for that world's own, sibling to `entry`/`policy`/`profile`/`portals` rather than nested inside `policy`. This deliberately does not follow §3.4.1's domain-default/world-override shape: a domain-wide calendar and any number of per-world calendars are meant to coexist as separate, simultaneously-visible schedules, never one falling back to or being overridden by the other. It's the same independent, either-can-be-true composition `chat`'s existing domain/world flags already use in this codebase's demo content (undocumented here, since chat itself never needed to leave the domain) — applied to a field that, unlike chat, genuinely does need to be legible outside the domain that created it (§10), since a visitor's own wallet is exactly what asks a *different* domain's client for its calendar when checking a favorited or typed-in remote domain. `GET /atlas/calendar` (optionally `?world={id}`) is ungated and unsigned — the same plain-HTTPS trust boundary the manifest and §7's catalog already rely on, no new signature scheme for a field that was always going to be public. `POST /atlas/calendar` is a real, protocol-level write endpoint, domain-operator-authenticated with no visitor signature involved, following §11.1's exact precedent for domain-to-subscriber mail: this spec takes no position on how a domain authenticates its own operator for it, only on the shape of what a conforming read returns. v1.22 is a documentation-only correction, no new behavior: §7 is caught up to a capability the reference implementation already built and shipped, sometime after v1.15, without this document ever catching up to it — a trading station settling a specific unique (`fungible: false`) asset, not only a fungible balance, through the exact same posted-listing/browse/claim mechanism, with `quantity` simply pinned to `1` on that side of the trade and settlement transferring the actual presented instance (preserving whatever per-instance state it already carried, e.g. a serial number or rolled properties) rather than minting a fresh one from the class's static definition. The catalog discovery paragraph (v1.18) is corrected the same way: a station's catalog was never actually filtered to `fungible === true` in the reference implementation, only to `tradeScope !== "bound"` — a unique, tradeable class was always meant to be discoverable there too, this document just never said so. Nothing about §7's trust properties, atomicity guarantee, or membership gate changes; a unique asset settles under the identical signed-intent-plus-presented-possession discipline a fungible balance always has. v1.23 is a documentation-only correction, no new behavior: §5.6 (**direct transfer**, `POST /atlas/asset/transfer`) and §5.7 (**redemption**, `POST /atlas/asset/redeem`) catch this document up to two capabilities the reference implementation already built and shipped without either ever being written down here — a plain, single-recipient, no-world, no-counterparty move authorized by nothing but the current owner's own signature, and its natural sibling, a holder revoking their own credential the same way, with no recipient at all. Both were already covered end-to-end by README.md's and issuer-php/README.txt's own implementation-level descriptions; this only gives them the protocol-level section every other endpoint in §5 already has. Nothing about §5's four verification steps, §5.3's revocation mechanism, or any existing endpoint's behavior changes — §5.6 reuses the same revoke-then-mint-fresh custody-change primitive §5.5's Claim step and §7's Settle step already share, and §5.7 reuses §5.3's revocation wholesale, just reached through a new authorization route. v1.24 adds §5.8, **purchasing with a balance**, and §5.9, **fulfillment** — the one transfer shape this spec still didn't have: acquiring something by spending part of a fungible balance, rather than being given a whole credential outright the way every mechanism through §5.7 already covers. §5.8 is deliberately generic: a catalog entry opts into being purchasable by declaring its own price (a class and an amount of it), and `POST /atlas/asset/purchase` debits a presented balance of that class by that amount while minting the purchased class fresh, in the same atomic act — nothing about the mechanism itself knows or cares what the purchased class represents, so the identical endpoint serves a spatial world's shop exactly as well as anything else a domain decides to sell this way. Authorization is the current balance owner's own signature (the same intent envelope §5.6 and §5.7 already use), never the domain operator's — spending your own balance is the buyer's call, the same standing §5.7 already gives a holder over their own credential's fate. §5.9 closes the other end for anything meant to be handed over once and only once: `POST /atlas/asset/fulfill` lets the domain operator confirm a presented credential is genuine and unrevoked, then consume it in the same act, reusing §5.3's revocation wholesale under a new reason code (`"fulfilled"`) the same way §5.7 already reuses it under `"issuer-request"` — the mirror-image authorization of §5.7, since here it's the operator attesting the hand-over happened, not the holder giving something up. Neither section changes any existing endpoint, credential shape, or trust property; both are new, additive mechanisms built entirely from primitives §5 already established. v1.25 adds §5.10, **time-based expiry** — a second, orthogonal way a credential stops being valid, alongside §5.3's revocation: an optional signed `asset.expiresAt`, present only on a credential whose class opted in at mint time, checked with nothing but arithmetic against the clock rather than a published list. A day pass, an event ticket, or anything else meant to self-invalidate after a fixed duration no longer needs an issuer to remember to revoke it on a schedule — the deadline travels inside the credential itself, signed once, alongside `asset`. Every place §5's mechanisms already check `id` against the revocation list now also checks `expiresAt` against the current time, rejecting either the same way; a museum day ticket, admitted once at the door via §5.9's fulfillment and priced through §5.8's purchase mechanism exactly like any other purchasable class, is the worked example, but nothing about the endpoint gains any ticket-specific logic to support it — a catalog entry declaring its own expiry duration is the entire opt-in. No existing field, endpoint, or trust property changes; a class that never declares an expiry duration behaves exactly as every class did before this version. v1.26 adds §5.11, **third-party attestations** — a domain can now sign its own statement about an asset it didn't issue (an independent review, a certification, a standing check) without needing the asset's own issuer to cooperate, grant custody, or even be aware the attestation exists. It reuses the exact same trust bootstrap §11.4's federation attestation and §5.5's cross-domain drop claim already established — fetch the ATTESTING domain's own `.well-known/atlas-key.json`, verify a signature against it — aimed at a new credential shape instead of a relay hop. Deliberately out of scope: how a domain authenticates whoever asks it to issue one, the same operator-authentication question §11.1 (mail) and §3.7 (manifest pinning) already leave to domain-local policy; this version only specifies the credential shape and how any client verifies one, not how a conforming domain decides to sign one in the first place. No existing endpoint, credential shape, or trust property changes. v1.27 adds §5.12, **clawback** — the one case where an issuer moves a credential without its current holder's consent: once a fraud report is confirmed, the issuer revokes the credential wherever it now sits and mints a fresh one straight to whoever it actually belongs to, in the same act. No new credential shape and no new verification steps a client needs to learn; the only addition is a second revocation reason code alongside `"transferred"` (§5.6) — `"clawback"` — so a client reading the revocation list can tell an issuer-forced recovery apart from a holder's own move, the same distinction `"fulfilled"` (§5.9) already draws against a holder-initiated `"issuer-request"` redemption. Unlike every other transfer mechanism in §5, `asset.tradeScope === "bound"` is deliberately not checked here — a relationship credential is exactly as recoverable as anything else once forced back through the issuer's own authority, since `tradeScope` disciplines what a holder may do, never what an issuer can do to correct one. Deliberately out of scope, same as it is everywhere else this spec touches trust: whether a given case really was theft, and whether a partially-spent or consolidated balance is only partly recoverable — this section specifies what happens once a human investigation reaches that conclusion, not how it gets there. v1.28 closes §7's and §11.4's long-standing "left unspecified"/"unresolved question" notes on cross-domain trade settlement — not with a mechanism, but with a decision not to build one: a trading station now explicitly settles only balances it issued itself, stated as a hard rule in §7 rather than left as a gap pending a future version. The reasoning is new, not just the rule: an open, anonymous listing is built so neither party needs to already trust the other, which is exactly the setting where a dishonest domain's unlimited, unaudited minting authority becomes a scalable way to defraud a visitor who never chose to hold that domain's credentials at all — a materially different and worse exposure than the same domain only ever being able to shortchange visitors who already extended it trust. §9 states this plainly as a security consideration in its own right, not folded into the existing "misbehaving trading station" bullet, since that one is about a station misbehaving and this one is about an honest station being used against an honest visitor by a dishonest third domain. §5.6's direct transfer (v1.23) already covers the legitimate cross-domain case — a visitor moving a specific asset to a specific counterparty elsewhere — and needed no change at all to do so, since it was always addressed by public key, not by domain. §11.4's closing note is reworded to match: trading was never actually blocked on an unresolved ledger question, and no future version is expected to revisit this. In the same paragraph, a stale cross-reference predating §5.6 (v1.23) is also corrected: §7's note that a station's mechanism doesn't replace direct, no-station transfer pointed at §5.2 (loadout loss-transfer, a different mechanism entirely — world-refereed, loser-co-signed) instead of §5.6, the section that actually defines it. v1.29 reverses v1.28's decision, but not its reasoning — the risk v1.28 identified (an open, anonymous listing lets a dishonest domain's unlimited minting authority defraud a stranger who never chose to trust it) was real and remains the operative concern; what changed is recognizing that a *mechanical* fix for atomicity (a two-phase lock/commit, already designed once before as a response to the signature-mismatch error a cross-domain listing produced pre-v1.28) and a *trust* decision about which domains to trade with at all are two separate questions, and v1.28 conflated them by treating the absence of the first as though it settled the second. §7 now specifies both, kept deliberately distinct: a per-domain, symmetric **trusted trade peers** allowlist (checked both as the station accepting a foreign balance, and as the issuer honoring another station's relay request against its own credential) is the trust gate, and a two-phase **lock** (suspend the credential against the pending trade, with a short self-expiring deadline instead of a separate unlock call) **then settle** (spend to the counterparty, remainder back to the original owner, via two new endpoints, `/atlas/trade/relay-lock` and `/atlas/trade/relay-settle`) is the atomicity mechanism, built on the same attestation-and-verify shape §11.4's federation relay and §5.5's cross-domain drop claim already established. §9's security-considerations bullet is rewritten to explain why the allowlist, not the lock/commit, is what actually makes this safe — an atomic trade with a party nobody chose to trust is still a successful fraud, just a tidier one. §11.4's closing note on trading being out of scope is revised rather than removed: trading now has a cross-domain mechanism, but a deliberately separate one from mail federation, authenticating a different thing (a station's own relay request against an issuer's credential, not a message's sender) through its own gate. v1.30 adds §3.8, **wallet bridge**: a world's `entry` field (§3) is now optional — an entry with none declares no enterable space at all, existing purely to carry a `policy` for a page that wants to opt into the capability below without being a spatial destination — and a new field, `policy.walletBridge` (with a domain-level `walletBridge` default), follows §3.4.1's existing domain-default/world-override shape to let a page ask whether a wallet identity is currently active and, if so, read its public key. Gated the same way every other policy field already is: absent everywhere means no access, matching this spec's existing posture that nothing gets a channel to a visitor's wallet for free just by existing. Deliberately read-only — asking the wallet to sign or mint something is a materially different, higher-stakes capability needing its own non-spoofable confirmation step and its own manifest-declared scoping, neither of which this version specifies; left for a future version rather than included here undercooked. v1.31 adds §3.8.1, the first of those two deferred pieces: a page may now ask the wallet to *sign* an application-defined payload through the same bridge, reusing §6.2's existing canonicalize-then-sign mechanism unchanged rather than inventing a second signature format. `policy.walletBridge.sign` (domain-default/world-override, same §3.4.1 shape `read` already uses) is an array of `purpose` strings a world will accept a signing request for, rather than a bare boolean — the manifest-declared whitelist §3.8's closing paragraph said this would need, scoped to the one field (`purpose`) a payload is required to carry rather than to a fixed action/class vocabulary, since an application-defined payload has no asset class of its own to whitelist. A purpose not on the effective list is refused immediately with no prompt shown at all, same as every other manifest-gated capability in this spec. A purpose that *is* on the list still requires the other piece §3.8 flagged as non-negotiable: a non-spoofable confirmation the requesting page cannot draw over, script into, or control the content of, showing the real requesting origin and the payload in plain language, approved or denied fresh for every single request — this version is explicit that no standing consent or cached approval is permitted here, unlike the reference implementation's own admin-session mechanism (outside this spec's scope) that deliberately does cache authorization, but for a different, extension-UI-originated flow a page's own script was never part of. Minting through the bridge remains unspecified, same as v1.30 left it — this version only ever produces a §6.2 proof envelope, never a credential. v1.32 adds §3.8.2, the piece §3.8.1's own closing paragraph named as still missing: a page may now *offer* a visitor a complete, already-signed `domain-atlas-asset/1.0` credential through the bridge — minted by the offering domain's own, ordinary same-origin issuance, never by the bridge itself, which only ever receives one. `policy.walletBridge.offer` (domain-default/world-override, §3.4.1 shape, same as `read` and `sign`) whitelists asset classes rather than purposes, refusing an unlisted class with no prompt, same posture as an unlisted signing purpose. A whitelisted class still requires §3.8.1's non-spoofable confirmation, naming the asset rather than a raw payload — but approval here is deliberately weaker than approving a signature: a conforming client MUST NOT add the credential to the wallet at that point, queuing it into a pending, sandboxed holding area instead, restating §11.2's existing "MUST NOT auto-adopt a gift on arrival" rule for this second arrival path rather than quietly letting a page-driven offer skip it. A later, separate, explicit Claim action is the only path that runs §5 step 1's real verification and adds the credential to the wallet; Dismiss discards a pending offer without ever claiming it. A per-identity trusted-domains mechanism that could skip the sandbox, and letting a visitor preview a pending offer before claiming it, are both left for a future version, the same one-capability-at-a-time pacing v1.30 and v1.31 already followed. v1.33 adds §3.8.3, the first of those two: a per-identity, visitor-maintained list of domains trusted to skip §3.8.2's confirmation and sandbox entirely for whatever classes that domain's manifest already has whitelisted — granted only through an explicit opt-in on the client's own trusted confirmation surface, never something a page can request or detect, and revocable the same way any other client-side list in this project already is. Preview-before-claim remains unspecified, left for its own future version exactly as v1.32 left it. v1.34 adds §3.8.4, that remaining piece: a conforming client MAY let a visitor inspect a pending offer's full asset — name, class, quantity, and whatever other §5 fields the credential carries — before choosing to Claim or Dismiss it, rendered the same way the client already renders anything already in the wallet. No wire format, page-visible capability, or manifest field changes; this is entirely client-side UI built on data the bridge was already handing the client once an offer reached the pending-offers sandbox §3.8.2 specified. Closing this was the last of the two gaps §3.8.2's own closing paragraph named — §3.8.3 already closed the other — which closes out the wallet-bridge capability as originally scoped by §3.8's own closing note: read, then sign, then offer, with sandboxing, trust, and now preview layered onto offer in turn. §3.8.2's and §3.8.3's own closing paragraphs are revised to point here instead of restating the gap as still open. v1.35 closes a real gap in §7's own two-phase lock/commit: the SETTLE half (`/atlas/trade/relay-settle`) was specified as a single attempt with no notion of retry, which is fine when the attempt is cleanly accepted or cleanly rejected but leaves a real ambiguity when the request reaches the credential's issuer, is fully applied there — including mailing the trade's absent poster their own side of it — and only the RESPONSE is lost in transit; the relaying station then has no way to tell that apart from the settle never having happened, and the mitigation v1.29 itself didn't yet have (refunding the claimant's own already-spent balance, added separately as a bug-fix that predates this version note) made it actively worse by revoking the very credential it had just told the issuer to mail out. `/atlas/trade/relay-settle` is now idempotent per (tradeId, credentialId): a repeat call carrying the exact same attestation that already succeeded replays the recorded result instead of either re-mutating anything or falling into "already revoked," and the relaying side now retries a failed settle attempt once, with the same attestation, before concluding it genuinely failed. This is a reliability fix to an existing mechanism, not a new capability — no new field is visible to a client, no new trust decision is introduced, and a domain that never retries and never replays behaves exactly as it did under v1.29. v1.36 adds §13, **email-delivered bearer credentials**: an opt-in way for a domain to hand a bearer-instrument credential (a ticket, voucher, or coupon) to someone with no wallet at all, held, transferred, and redeemed entirely through an ordinary inbox — a new top-level manifest field, `emailTickets` (sibling to `calendar`, §12, for the identical single-per-domain reason), a forward-to-CC transfer mechanic with instant reissue, delivery-check-before-revoke, and VERP-correlated bounce reversal, and a new self-serve redemption endpoint modeled on this implementation's own `/atlas/demo/*` bearer pattern rather than §5.6's/§5.7's holder-signature one, since an email-only recipient has no keypair to sign anything with. Closes the one real mechanism gap the design surfaced before any of this could be built: `suspend()` (already relied on by §7's own Lock step) gets a fourth, optional `onExpire: "lift" | "finalize"` argument, defaulting to `"lift"` — every suspension created before this version, and every call site that doesn't pass it, keeps exactly today's behavior — so a door-scanned ticket can be suspended for an event's own duration and finalize to a genuine revoke (reason `"redeemed"`, alongside a new `"email-transferred"` for the transfer step, §5.3) once that window closes, rather than silently reactivating the way every suspension before this version always has. No existing endpoint, credential shape, or trust property changes for anyone not using this new section. v1.37 closes a real gap §13 left open — it specified the wire format a ticket travels in (§13.2) and what happens once it's forwarded (§13.3) or redeemed (§13.4), but never said how a ticket enters the system in the first place. §13.1 now specifies that entry point: `POST /atlas/asset/transfer-to-email`, a sibling to §5.6's direct transfer that targets an email address instead of a recipient's public key, authorized and verified identically, reusing §5.6's exact mint-then-revoke custody change. This surfaced a second small gap closed in the same edit: §5's `owner.publicKey` is a required signed field, but an email-delivered credential has no wallet, and so no real key, on the receiving end. §13.1 resolves it the same way bearer authority is resolved everywhere else in this section — the field is populated with a keypair the issuer generates and immediately discards, satisfying the existing credential shape without implying anyone holds a working private key behind it; nothing in §13.3 or §13.4 ever checks it again. No existing endpoint, credential shape, or trust property changes for anyone not using §13. v1.38 adds §3.8.5, a fourth wallet-bridge capability alongside read, sign and offer: a page that already holds a complete credential (one it just minted, say) may ask the wallet to show it in the client's own trusted preview surface, so a page can offer the same hover preview the client gives items in a world. It is opt-in through a new top-level manifest field, `fileTransfer`, and adds two revocation reason codes.

## 1. Overview

Domain Atlas lets any existing domain declare a spatial presence — one or more places a visitor can enter, look around, move between, and optionally carry owned assets across. It adds nothing to the network layer. Everything here sits on top of standard HTTPS, WebXR, and WebAuthn, and reduces to four things:

1. A **manifest** a domain publishes at a well-known path, so a client can discover that a spatial presence exists — one manifest, one or more declared **worlds**.
2. An **asset credential** format covering both unique ownership claims (a compass, a badge) and fungible ones (fuel, raw materials, currency) in one shape, distinguished by a signed `fungible` flag rather than by two separate credential types — verifiable by any domain without trusting the issuer, a shared registry, or a token, a chain, or a gas fee.
3. An **identity flow** built on WebAuthn passkeys, where a person's identity is a public key, and email — if used at all — never reaches a visited domain.
4. A **trading mechanism** (§7) that lets two visitors — and the independent worlds their fungible assets came from — complete a live exchange without a blockchain and without either side being able to walk away holding both sides of the trade.

Nothing here requires a new URI scheme, a new port, or client software beyond a conforming browser extension or, eventually, native browser support.

**The one rule everything else follows** (expanded in §10): the protocol carries only what has to survive leaving the domain — identity, ownership, and the minimum a stranger needs to find and understand a space before entering it. Everything that only matters inside one domain — who can build where, land records, combat balance, quest logic, in-world chat — stays the domain's own business and this spec has nothing to say about it.

## 2. Terminology

- **World** — one declared space a visitor can enter, look around, and move through.
- **Manifest** — the JSON document at `/.well-known/spatial.json` declaring a domain's world or worlds.
- **Portal** — a declared link from one world to another, same-origin or cross-origin.
- **Asset** — anything a visitor can own, represented by one signed credential shape (§5). A `fungible: false` asset (a compass, a badge) is unique and moves as a whole; a `fungible: true` asset (a raw material, fuel, currency) is a stackable quantity that can be split and combined. Same credential, same verification, different value for one signed field.
- **Wallet** — the client-side store of a visitor's credentials, balances, and keys. Never transmitted whole; individual credentials are presented on request.
- **Loadout** — the subset of a wallet a visitor has explicitly brought into one world's active session.
- **Identity** — a public key. Not a username, not an email address. Ordinarily WebAuthn-derived (hardware-backed, private key never leaves the authenticator); §6 also allows a client to offer a local-password-derived keypair as an explicitly lower-assurance alternative. Either way, the protocol only ever tracks the public key.
- **Anchor** — a named waypoint inside a scene, letting a link enter a world at a specific location rather than only its default spawn point.
- **Key-anchored world** — a world whose manifest is authenticated by its own signature and public key instead of by domain ownership (§3.6). Every world described before §3.6 is domain-anchored, the default this spec assumes unless it says otherwise.

## 3. The manifest

Served at `https://{domain}/.well-known/spatial.json`, `Content-Type: application/json`, cacheable, publicly readable. One manifest per domain, declaring one or more worlds:

```json
{
  "spec": "domain-atlas/1.0",
  "domain": "example.com",
  "owner": {
    "name": "Example Inc.",
    "contact": "spatial@example.com"
  },
  "calendar": true,
  "defaultWorld": "plaza",
  "worlds": [
    {
      "id": "plaza",
      "name": "Example Plaza",
      "entry": {
        "scene": "/spatial/plaza/scene.json",
        "renderer": ["procedural-v1", "gltf"]
      },
      "calendar": true,
      "policy": {
        "guestAccess": "open",
        "discoverable": true,
        "identityRequired": false,
        "itemDropsAllowed": true,
        "acceptedItemClasses": ["atlas.wearable", "atlas.badge"],
        "trustedIssuers": "any"
      },
      "profile": {
        "genre": "fantasy-marketplace",
        "scale": "planet",
        "capabilities": {
          "building": "owner-only",
          "vehicles": true,
          "combat": "pve",
          "landOwnership": true
        }
      },
      "portals": [
        { "kind": "world", "to": "museum", "label": "Enter the Museum" },
        {
          "kind": "domain",
          "to": "neighbor.example",
          "label": "Visit Neighbor",
          "manifest": "https://neighbor.example/.well-known/spatial.json"
        }
      ]
    },
    {
      "id": "museum",
      "name": "Example Museum",
      "entry": { "scene": "/spatial/museum/scene.json", "renderer": ["procedural-v1", "gltf"] },
      "policy": {
        "guestAccess": "open",
        "discoverable": true,
        "identityRequired": false,
        "itemDropsAllowed": false,
        "acceptedItemClasses": [],
        "trustedIssuers": "self"
      },
      "profile": {
        "genre": "gallery",
        "scale": "building",
        "capabilities": { "building": "none", "vehicles": false, "combat": "none", "landOwnership": false }
      },
      "portals": [
        { "kind": "world", "to": "plaza", "label": "Back to the Plaza" }
      ]
    }
  ],
  "updated": "2026-08-22T00:00:00Z"
}
```

Field notes:

- `worlds` is always an array, even for a domain with exactly one world. Nothing about the single-world case is more complicated for it — it's a `worlds` array of length one, `defaultWorld` pointing at it.
- `defaultWorld` is which world a plain visit to the domain resolves to — what a generic client offers first.
- `entry.renderer` is an ordered preference list; a client renders the first entry it supports. `gltf` points `entry.scene` at a `.gltf`/`.glb` asset for production use. `procedural-v1` (§3.2) is a lightweight fallback for spaces that don't want to author 3D assets — what the reference prototype uses.
- `portals[].kind` is `"world"` or `"domain"`. A `"world"` portal is a same-origin scene swap — `to` names another entry in this same manifest's `worlds` array, no network round-trip, no re-verification of anything, because the trust boundary never changed. A `"domain"` portal crosses to a different domain entirely — `to` names it, `manifest` points at its own `/.well-known/spatial.json`, and everything about crossing a real trust boundary (§5, §6) applies in full.
- `policy.guestAccess` (`"open" | "invite-only" | "private" | "closed"`) and `policy.discoverable` (`true`/`false`) are separate on purpose — "who can enter" and "who can find this at all" are different questions. A world can be wide open to anyone with the address but still `discoverable: false`, the spatial equivalent of an unlisted link. Both are enforced by the domain's own backend, not the client; the manifest states intent, the domain remains the authority.
- `policy.identityRequired` (`true`/`false`) — whether a visitor needs an identity (§6) before entering, independent of `guestAccess`/`discoverable`. Unlike those two, this one CAN'T be enforced by the domain's backend even in principle — a domain has no way to observe a visitor's wallet state before a scene ever loads — so a conforming client is the enforcement point here, not an advisory hint the client is free to ignore. Follows the same domain-level-default, per-world-override shape as §3.4.1.
- `calendar` (`true`/absent, default absent) — opts a domain, and independently any one world, into publishing a schedule of events (§12). A top-level `calendar: true` means the domain itself has a domain-wide calendar; a world's own `calendar: true` means that world has its own, separate calendar. Both may be `true` at once, and neither implies or overrides the other — this is deliberately NOT §3.4.1's domain-default/world-override shape, since the two calendars (if both exist) are meant to be discovered and shown side by side, not resolved into one effective value. See §12 for the fetch/authoring endpoints this field enables.
- Absence of this file at the well-known path simply means the domain has no declared space. No error, no penalty — adoption is opt-in and additive, the same way a missing `robots.txt` is silently fine.

### 3.1 One manifest, many worlds — or many domains

A domain with several distinct spaces has two genuinely different mechanisms, and which one fits is a real decision:

**Subdomains** need nothing beyond what §3 already describes. `plaza.example.com` and `museum.example.com` are different origins as far as DNS and the browser are concerned, so each gets its own manifest, its own trust root, its own hosting, connected only by an ordinary `"kind": "domain"` portal. Use this when the worlds genuinely need separate operation — different teams, different hosting, different legal entities, a franchise where each location runs its own world under its own rules.

**One manifest, several `worlds`** is the other option. Every world in it shares one identity, one owner record, one signing key for asset issuance (§5) — a visitor who trusts `example.com` trusts all of its worlds equally, and moving between them is a same-origin scene swap rather than a fresh trust decision. Use this when one operator wants several distinct spaces that should feel like rooms in one building, not separate establishments.

The two compose freely. Nothing stops a domain from having three internal worlds *and* a portal out to a fully separate partner domain — a client doesn't treat either as more "real" than the other, only as carrying different trust. The one rule that never bends: identity and item trust follow the domain boundary, never the world boundary. Worlds inside one manifest are as trusted as each other by construction; a domain reached by a `"domain"` portal is exactly as trusted as any address typed into a browser, because it is one.

### 3.2 Procedural scenes

For worlds that don't want to author glTF assets, a `scene.json` can describe a space procedurally instead:

```json
{
  "format": "procedural-v1",
  "floor": { "size": [20, 20], "color": "#1b2830" },
  "objects": [
    { "type": "box", "position": [0, 1, -3], "size": [1, 2, 1], "color": "#c05a1f", "label": "Welcome" }
  ],
  "portalMarkers": [
    { "position": [5, 0, 0], "portalIndex": 0 }
  ]
}
```

`portalMarkers[].portalIndex` indexes into that world's own `portals` array, so a client can place a walkable doorway at a specific point in the scene rather than only as a UI button.

`interactables` is the same idea applied to a world's own on-the-ground fixtures rather than its exits — a clickable point in the scene tied to a client-side action, e.g. `{ "position": [-2, 0.5, -1], "label": "Mine Iron", "action": "issue", "class": "atlas.element.iron", "quantity": 20, "role": "self" }` for a fungible-asset stall, or `{ "position": [-4, 0.5, -2], "label": "Bronze Compass", "action": "issue", "class": "atlas.wearable", "oncePerUser": true }` for a unique-asset stall — one `action`, `quantity` present or absent depending on whether `class` names a fungible or non-fungible asset (§5). Unlike `portalMarkers`, nothing here needs a manifest cross-reference — every field an action needs travels with the marker itself. This is reference-prototype convenience, not a new protocol primitive: `interactables` itself is unsigned scene data, same as `portalMarkers` — clicking one just triggers the ordinary, already-signed §5 issuance flow a visitor could otherwise reach through a settings panel, nothing about the credential that comes out of it is any different. `oncePerUser` is a client-side courtesy on top of that (checking this wallet's own assets before asking for another) — the protocol itself has no concept of scarcity, so this is a per-device nicety, not real enforcement.

### 3.3 Discovery

A world's `policy.discoverable` flag (§3) is what matters here — the difference between "enterable if you have the address" and "surfaced in directories and search."

**Bootstrap.** The end state looks like `sitemap.xml`: a crawler that already indexes the web adds "also check `/.well-known/spatial.json`" to its routine, the same low-cost addition sitemaps and Open Graph tags were for search engines and social platforms. That only happens once there's enough adopted content to be worth indexing, and nothing is adopted yet — the same bootstrap problem as the protocol itself, one layer up. The fix is not to wait for a major search engine: a reference implementation ships its own minimal, open directory, seeded by self-submission the way early web indexes were submitted links before crawling had a large enough graph to work from.

**A concrete interface**, so this isn't left as a suggestion:

- `POST /submit` — `{ "manifest": "https://mydomain.com/.well-known/spatial.json" }`. The directory fetches it, validates `spec` and shape, and indexes every world marked `discoverable: true`.
- `GET /search?genre=...&scale=...&combat=none` — returns matching worlds (domain, world `id`, `name`, a short description drawn straight from the manifest).

A submission naming a key-anchored world (§3.6) is verified the same way any client would verify one, not taken on faith: the directory fetches the manifest and confirms `signature` actually checks out against the submitted `identityKey` before indexing it. Search results distinguish domain-anchored and key-anchored listings rather than presenting them identically, so a client — or a visitor reading directory results directly — can decide how much weight to give each without the directory quietly flattening a real difference.

For ranking, before reaching for anything more elaborate: the count of inbound `"kind": "domain"` portals pointing at a manifest is a simple, self-computed relevance signal — the same insight PageRank started from, applied to a much smaller graph. A world other domains bother to portal to is doing something worth finding. Multi-world manifests give this a small efficiency for free: one fetch indexes every discoverable world a domain has, not one fetch per world. Anyone may run a competing directory against the same public manifests; nothing here designates one as canonical.

### 3.4 Categorization and trust

Two more things a manifest declares, both purely advertisement — a directory or client uses them to filter and warn, no enforcement lives here:

- **`profile`** — `genre` (free text, e.g. `"fantasy-marketplace"`), `scale` (`"room" | "building" | "district" | "planet" | "system" | "galaxy"` — useful for a world that's mostly a portal directory to describe itself as a `"system"` rather than a `"room"`), and `capabilities` (`building`, `vehicles`, `combat`, `landOwnership`) describing what kind of space this is before anyone walks in. `capabilities.building` is `"none" | "owner-only" | "residents" | "anyone"` — a coarse advertisement of policy, not the policy engine itself; the domain's own backend decides who actually counts as a "resident." `capabilities.combat` is `"none" | "pve" | "pvp"` and matters directly to §5.2.
- **`policy.trustedIssuers`** — `"any"` | `"self"` | an explicit array of issuer domains. Independent of `acceptedItemClasses`: class governs *what kind* of item a world knows how to render; `trustedIssuers` governs *whose* items it's willing to render at all. A world can run a closed economy (`"self"`), an open one (`"any"`), or a curated one (an explicit allowlist) — three real, different products, one field.

None of this requires hosting anything beyond the manifest itself. A domain's actual asset catalog — models, textures, authoring tools — is ordinary web hosting and application logic, entirely the domain's business; nothing here standardizes how a domain manages its own inventory, only how another domain decides whether to trust what comes from it.

### 3.4.1 Domain-level defaults, per-world overrides

Several fields that live on a world's own `policy` are also meaningful one level up, at the top of the manifest, as a domain-wide default every world falls back to unless it says otherwise. The rule is the same everywhere this shows up: **a world's own value, when present, always wins outright** — including an empty array or an explicit `false` — the domain-level value only fills in when the field is absent from that world's `policy` entirely. A domain sets its default once instead of repeating it on every world; any one world can still opt itself out, or in, without touching the rest, and without the domain-level value ever silently overriding an explicit per-world choice.

`policy.acceptedItemClasses` is the reference case: a domain can declare `"acceptedItemClasses": [...]` once at the top level, and every world inherits it unless that specific world's own `policy.acceptedItemClasses` is present — including an explicitly empty `[]`, which means "this world accepts nothing," not "fall back to the domain default." Any future per-world policy field that a domain plausibly wants to set once for every world it owns (a visitor-identity requirement, an opt-out from direct/quick-travel entry, and so on) should default to this same shape rather than inventing a new one — it's already the established convention here, not a one-off.

This is a manifest-authoring convention for how such a field composes, not new protocol machinery — a client resolves it by checking the world's own `policy` first and falling back to the manifest's top level, nothing more.

### 3.5 Per-page discovery and anchors

Everything above works at the domain level — one manifest advertising the worlds a domain has as a whole. That's the right level for a directory or a crawler (§3.3), but it's the wrong level for a visitor already looking at one specific page: a product listing, a blog post, a portfolio piece. That page usually corresponds to something narrower than "the domain's world" — a specific room, a specific display, a specific place — and until now there's been no way for the page itself to say so; every visitor lands at the same `defaultWorld` front door regardless of which page brought them there.

A page opts in with one `<link>` tag in its own `<head>`, the same pattern `<link rel="alternate">` and Open Graph tags already use for per-page metadata:

```html
<link rel="spatial" href="/.well-known/spatial.json#plaza:aisle-12">
```

The fragment names a target inside that domain's existing manifest — `{worldId}` alone drops the visitor at that world's normal entry point, `{worldId}:{anchorId}` drops them at a specific named point inside it. A conforming client checks the current page for this tag before falling back to the domain-wide manifest and its `defaultWorld` — precision when a page offers it, the existing behavior when it doesn't.

This deliberately reuses the domain's already-declared worlds rather than letting a page invent a disconnected space of its own. A world only one page ever links to behaves, in effect, like that page's own standalone space — nothing requires any portal or other page to point at it. A page that links to `plaza:aisle-12` instead reads as a location inside the domain's larger, shared place. Both are the same declaration at different scales; a site owner doesn't choose between "own space" and "location in our space" in the abstract, they choose per page, and the two never collide because they're the same mechanism.

**Anchors** are the one small addition this requires to `scene.json` (§3.2) — named waypoints inside a scene, not just the single implicit spawn point a world has today:

```json
{
  "format": "procedural-v1",
  "floor": { "size": [40, 40], "color": "#1b2830" },
  "objects": [ ],
  "portalMarkers": [ ],
  "anchors": [
    { "id": "aisle-12", "position": [4, 0, -2], "label": "Aisle 12 — Hardware" }
  ]
}
```

`anchors` is optional and additive — a scene with none behaves exactly as it does today. A world only needs to name anchors for the places it expects to be linked to directly; nothing requires anchoring every corner of a large space up front, only the ones a page actually points at.

This costs nothing at the trust layer. §3.1's rule holds without change: identity and asset trust still follow the domain boundary, never the world boundary — an anchor is only ever a position inside a world the domain already declared and already owns the policy for, never a new trust surface of its own.

### 3.6 Key-anchored worlds — spaces without a domain

Everything above assumes a world's trust comes from a domain: whoever controls the DNS and the TLS certificate controls what the manifest says, and that's the entire basis for believing any of it. That's a deliberate choice, and a good one for anything that wants to be found and recognized at a glance — but it also means the barrier to publishing a world is the barrier to owning a domain: money, DNS, hosting. Not everyone who wants a space clears that bar, and nothing about the credential mechanisms in §5 or §6 actually requires it — an asset credential is already trusted by its signature, not by where it's hosted. A **key-anchored world** applies the same idea to the manifest itself.

Instead of `domain`, its manifest carries the owner's own public key and a signature over its own content:

```json
{
  "spec": "domain-atlas/1.0",
  "identityKey": "base64url-space-owners-public-key",
  "owner": {
    "name": "Alex's Workshop",
    "contact": "alex@example.net"
  },
  "defaultWorld": "workshop",
  "worlds": [ ],
  "updated": "2026-08-25T00:00:00Z",
  "signature": "base64url-signature-over-canonical-manifest-minus-signature"
}
```

`worlds` inside a key-anchored manifest is the exact same shape §3 already defines — worlds, portals, policy, profile, nothing about them changes. A manifest with `domain` is domain-anchored, verified exactly as §3 already describes: trust comes from TLS and DNS, nothing new. A manifest with `identityKey` and no `domain` is key-anchored: a client verifies it by canonicalizing the manifest with `signature` removed (§6.2's canonicalization, reused unchanged) and checking `signature` against `identityKey`. Its authenticity doesn't depend on where the file happens to be hosted — a directory service, a personal file host, anywhere willing to serve JSON over HTTPS — because the proof travels with the content instead of being vouched for by whichever server happens to be holding it.

A portal or directory entry names a key-anchored world by its key, not a hostname:

```json
{
  "kind": "key",
  "identityKey": "base64url-space-owners-public-key",
  "manifest": "https://directory.example/spaces/alex-workshop/spatial.json",
  "label": "Visit Alex's Workshop"
}
```

A client fetches `manifest`, verifies its signature against `identityKey`, and confirms both match the portal's own declared `identityKey` — so nothing hosting that URL can quietly swap in a different key-anchored world underneath an existing link.

**Issuing assets without a domain.** Nothing in §5 requires a domain either — an asset is already trusted by its issuer's signature, not its address. An issuer's key document today lives at `https://{issuer.domain}/.well-known/atlas-key.json`, a location only meaningful because of domain ownership. A key-anchored issuer instead names that document directly: `issuer` on an asset credential may be `{ "identityKey": "...", "keyDocument": "https://wherever-its-hosted/atlas-key.json" }` in place of `{ "domain": "...", "publicKey": "..." }`. Verification step 1 in §5 generalizes accordingly — fetch whichever key document the credential actually names — everything after that (confirming validity at `issuedAt`, checking the signature, checking revocation) is unchanged.

**What this deliberately doesn't solve.** A domain is scarce and human-legible — nobody else can be `anthropic.com`, and a stranger can recognize that string on sight. A public key is neither: anyone can generate as many as they like, and nobody can eyeball one and know whose it is. A key-anchored world's signature proves the manifest wasn't tampered with and genuinely came from whoever holds that key — it proves nothing about who that is. That's not a flaw to quietly work around; it's the actual trade-off for not needing a domain, and §3.6.1 exists because a client can't be honest with a visitor without saying so plainly.

Nothing stops a key-anchored world from later adding a real domain without losing continuity. §3.7's optional domain identity pinning is exactly the field for it: a domain-anchored manifest can publish the same `identityKey` its key-anchored past used, and a client that's seen both can treat it as one continuous world rather than two unrelated ones.

### 3.6.1 Client trust signaling

A conforming client must never render a key-anchored world the same way it renders a domain-anchored one — silently treating both as equally trustworthy would erase exactly the distinction §3.6 exists to be honest about. Before entering one, a client must show a real, unavoidable disclosure — not a dismissible toast, not fine print — the same way §5.2 already requires a real warning before loading an item into a PvP world:

- **Any key-anchored world**, at minimum: a clear statement that this space isn't tied to a registered domain, and that its identity rests entirely on a cryptographic key the visitor has no independent way to recognize.
- **A key-anchored world absent from every directory (§3.3) the client checks** — reached only by a raw link, a pasted address, a QR code — is stronger still: nothing beyond that one link vouches for it at all. A client should present this the way a browser presents an invalid-certificate page: a real interstitial requiring an explicit, deliberate action to proceed, not a warning that quietly gets out of the way on its own.
- **A key-anchored world listed in at least one known directory** may say so in its disclosure — being indexed is a weak positive signal, since a directory can at least confirm the signature checks out and the entry hasn't been reported (§8) — but a client must not present that listing as equivalent to domain ownership. It isn't.

**Plain HTTP, for either anchor type, is worse than either warning above and must block harder.** This is independent of which trust model a world uses, and worth being exact about why. A key-anchored manifest's `signature` still protects its integrity even if fetched over plain HTTP — tampering breaks the signature regardless of transport — but the connection itself is now unencrypted and unauthenticated at the transport layer, open to monitoring or blocking. A domain-anchored manifest has it worse: TLS was never just encryption for it, it was the *entire* mechanism proving domain ownership, so a domain-anchored manifest fetched over plain HTTP has silently lost its whole basis for trust — worse off than an honestly-labeled key-anchored world, which at least still has its own signature to fall back on. A conforming client must treat any manifest, scene, key document, or issuance endpoint fetched over plain HTTP as a hard failure requiring explicit override, the same way a browser treats its own bad-certificate interstitial, and must never silently downgrade a failed HTTPS fetch into a "working" HTTP one.

### 3.7 Optional domain identity pinning

§3.6 gave a world without a domain its own signature to be trusted by. This section gives that same signature to a world that *has* a domain, for a different reason — not to replace TLS and DNS as the first-contact trust root, which they already do well, but to give a visitor's client something to notice with on every visit after the first.

A domain-anchored manifest may optionally add two fields alongside `domain`:

```json
{
  "domain": "example.com",
  "identityKey": "base64url-current-public-key",
  "signature": "base64url-signature-over-canonical-manifest-minus-signature"
}
```

`identityKey` names the domain's current signing key; `signature` covers the canonical manifest with `signature` itself removed, verified exactly as §3.6 already describes — the same canonicalization §6.2 defines, reused a third time now. The key it points at lives in the same rotation-safe document §5.3 already defines for issuer keys — `.well-known/atlas-key.json` — whether or not this domain runs an item issuer at all; a domain with no items to issue may still publish one purely to back this signature, and a domain that does issue items may reuse the same key for both or keep them entirely separate — §5.3.1 covers running more than one concurrently valid key for exactly this kind of purpose separation.

**What a client actually does with this.** On a first visit, nothing changes — there's no memory to compare against, so `identityKey` adds nothing a new visitor didn't already get from TLS and DNS, and a client that ignores this section entirely loses nothing it had before. The value shows up on a *return* visit: a client that chooses to remember a domain's `identityKey` (this is opt-in for the client, exactly as publishing it is opt-in for the domain) can compare what it remembers against what the manifest declares today. A changed key that the domain's current key-history document also lists as a deliberately rotated prior key is an ordinary, expected event — no different from any other key rotation in §5.3, and worth no more than a routine update to what the client remembers. A changed key with no rotation record anywhere is the actual signal: the domain still passes TLS, DNS still resolves, and the certificate is still perfectly valid, yet something a repeat visitor previously verified has quietly changed underneath all of that. A client should disclose this plainly rather than staying silent about it — but, deliberately, it should not hard-block the way §3.6.1 requires for a key-anchored world or plain HTTP. The domain's ordinary trust basis hasn't broken; this is one additional, optional signal layered on top of it, not a replacement for it, and treating an unexplained key change as an unrecoverable lockout is precisely the mistake HTTP Public Key Pinning made before browsers walked it back. A domain that loses its identity key, or never rotates it correctly, should end up with a client that's mildly suspicious on next visit — never one that refuses to load the site at all.

**A second, smaller use.** The same `identityKey` may appear on more than one domain's manifest — an operator running several domains, or a domain and a partner-hosted subdomain, can publish the same key on each to signal they're the same publisher without needing a shared parent domain to prove it. A directory (§3.3) or reputation feed (§8) may use this to link entries belonging to one operator, but a client should trust that link exactly as much as the signature backing it and no more — it's a claim the operator is making about themselves, not an independent confirmation from anyone else.

### 3.8 Wallet bridge — a page talking to the wallet directly

Everything above assumes a visitor who has already opened a conforming client's own wallet UI and clicked something inside it. This section gives an ordinary web page — no spatial scene required, not even a manifest that declares one otherwise — a way to ask that same wallet something directly from its own script, gated by the identical manifest mechanism a spatial world already uses to declare policy.

A `worlds[]` entry's `entry` field (§3) is now OPTIONAL. An entry with none declares no enterable space at all — it exists purely to carry a `policy`, for a domain that wants to opt a page into the capability below without that page being a spatial destination. A conforming client must never offer such an entry as something to walk into: it's never eligible to be `defaultWorld`'s resolution target, and never rendered as an Enter-style affordance. The one thing it's for is being the `id` a page's own `<link rel="spatial">` tag (§3.5) names — the exact same per-page linking mechanism §3.5 already defines, reused unchanged rather than inventing a second way for a page to point at one entry in a domain's manifest.

`policy.walletBridge` is a new world-level field, shaped `{ "read": true | false }`, declaring whether a page overriding to this world (§3.5) may ask the wallet bridge a read-only question: whether an identity is currently active and, if so, its public key. It follows §3.4.1's domain-default/world-override shape exactly, the same as `acceptedItemClasses` — a top-level `walletBridge` on the manifest is the domain-wide default every world falls back to, and a world's own `policy.walletBridge`, when present, always wins outright over it. The hard default when neither is declared anywhere is `false`: a page gets no bridge access at all unless a domain explicitly opts it in, matching the posture already established for `trustedIssuers` and `uniqueIdentity` — nothing gets a channel to a visitor's wallet for free just by existing.

A page with no `<link rel="spatial">` tag at all has no world-level override to check in the first place; only the domain-level `walletBridge` default applies, the same as any other §3.4.1 field resolves outside a world context.

```json
{
  "walletBridge": { "read": true },
  "worlds": [
    {
      "id": "checkout",
      "name": "Checkout",
      "policy": { "walletBridge": { "read": true } }
    }
  ]
}
```

**What this version deliberately doesn't specify.** A page asking the wallet to sign or mint something is a different, higher-stakes capability than reading a public key — it needs a non-spoofable confirmation step a page can't draw over or fake the contents of, and its own manifest-declared scoping over which specific actions and asset classes a page may invoke, before it can be specified responsibly. Neither exists yet. This version's `walletBridge` field grants read access only; a client implementing it must not treat any other value, present or future, as authorization for anything beyond that.

### 3.8.1 Wallet bridge — signing

§3.8 above specifies read access only and names signing as a separate, higher-stakes capability deliberately left out of that version. This section is that capability.

`policy.walletBridge.sign` is a sibling field to `policy.walletBridge.read`, inside the same `walletBridge` object, and follows the identical §3.4.1 domain-default/world-override composition — a world's own `sign` array, when present (an empty array counts as present, the same convention `acceptedItemClasses` already established), wins outright over a top-level domain default; the hard default when neither declares it anywhere is an empty list, meaning no signing capability at all. Unlike `read`, `sign` is never a bare boolean: its value is an array of `purpose` strings, the manifest-declared whitelist §3.8 said this capability would need before it could be specified responsibly.

```json
{
  "walletBridge": { "read": true, "sign": ["login"] },
  "worlds": [
    {
      "id": "checkout",
      "name": "Checkout",
      "policy": { "walletBridge": { "read": true, "sign": ["login", "age-attestation"] } }
    }
  ]
}
```

A page requests a signature by handing the wallet bridge an application-defined payload object — the same free-form kind of object §6.2 already signs for co-signed transfers and trade intents, with exactly one additional requirement here: the payload MUST carry a top-level string field named `purpose`. A conforming client checks that `purpose` against the effective `sign` array (the composition above) before anything else happens. A `purpose` not on that list is refused immediately — no confirmation prompt, no signature, nothing the requesting page can distinguish from the capability simply not existing. This is deliberately the same "never bothers the visitor with something not even declared" posture every other manifest-gated capability in this spec already takes; a page has no way to probe which purposes a domain hasn't opted into beyond the one it already knows to ask for.

A `purpose` that IS on the list still requires the other piece §3.8 named as non-negotiable: a confirmation step rendered as the client's own trusted UI, not the requesting page's — something the page cannot draw over, script into, read the contents of, or dismiss on the visitor's behalf — showing the actual requesting origin (never a value the page itself supplies or claims) and the payload in a human-readable form, with the visitor's explicit approval required before a signature is ever produced. This is required for every single request; a conforming client MUST NOT cache or auto-approve a later request for the same purpose and origin just because an earlier one was approved. That's a deliberate departure from mechanisms elsewhere in this project that do cache authorization (an admin session, outside this spec's scope, logs an identity into a domain's admin roster for a run of actions after one signature) — those exist for a visitor acting through the client's own trusted UI across a sequence of their own deliberate actions; this is a page's own script asking for one specific signed artifact, and every such artifact gets its own fresh, explicit decision.

On approval, the client signs the payload exactly per §6.2 — canonicalize, sign, wrap in the `"webauthn"` or `"raw-ecdsa"` proof envelope, whichever the active identity mechanism produces — and hands that envelope back to the requesting page. On denial, or when there's no active, unlocked identity to sign with at all, the page receives no envelope; a conforming client must not distinguish these two outcomes to the page in any way that would let it infer whether a wallet exists versus whether a human declined it, since either answer is simply "no signature," never a basis for the page to act on further.

**What this version still doesn't specify.** Minting a new credential through the bridge remains exactly as unspecified as §3.8 left it — this section only ever produces a §6.2 proof envelope over a page-supplied payload, never a signed `domain-atlas-asset/1.0` credential. A bridge call that could cause something new to arrive in a visitor's wallet needs its own answer for a risk signing doesn't have at all: nothing here lets a visitor end up holding an asset they never meant to accept, because nothing here mints one.

### 3.8.2 Wallet bridge — offering assets

§3.8.1's closing paragraph named the gap this section closes: nothing specified so far lets a page cause a new credential to arrive in a visitor's wallet. This section gives that capability its own gate, its own confirmation requirement, and — unlike signing — a mandatory non-adoption rule, since minting carries a risk signing never did: a visitor ending up holding something they never meant to accept.

`policy.walletBridge.offer` is a second sibling field inside the same `walletBridge` object as `read` and `sign`, following the identical §3.4.1 composition: a world's own `offer` array, when present (an empty array counts as present, the same convention `sign` already established), wins outright over a domain-level default; the hard default when neither declares it anywhere is an empty list, meaning no offer capability at all. Its values are asset classes, not purposes — the same vocabulary §5's `asset.class` and `policy.acceptedItemClasses` already use, since what's actually at stake here is which *kinds of things* a domain is willing to let a page hand to a visitor, not which action a payload is for.

```json
{
  "walletBridge": { "read": true, "sign": ["login"], "offer": ["com.example.shop.receipt"] },
  "worlds": [
    {
      "id": "checkout",
      "name": "Checkout",
      "policy": { "walletBridge": { "read": true, "offer": ["com.example.shop.receipt", "com.example.shop.coupon"] } }
    }
  ]
}
```

A page offers an asset by handing the wallet bridge a complete, already-signed `domain-atlas-asset/1.0` credential (§5) — minted by the page's own domain through whatever ordinary same-origin issuance mechanism that domain already runs. This bridge never mints anything itself; it only ever receives a credential someone else already produced, and decides what to do with it. `asset.class` is checked against the effective `offer` array above before anything else happens, with the same refusal posture §3.8.1 established for an unlisted `purpose`: a class not on the list is refused immediately, no prompt, nothing a page can use to tell "not whitelisted" apart from "capability doesn't exist."

A class that IS on the list still requires §3.8.1's confirmation step, shown the same non-spoofable way — naming the asset (name, class, quantity) here rather than dumping a raw payload, since that's what a visitor actually needs to recognize in this case. But approval here means something deliberately weaker than it does for signing: **a conforming client MUST NOT add the credential to the visitor's wallet on approval.** It queues into a pending, sandboxed holding area instead — inert, not yet owned — restating §11.2's existing rule ("a conforming client MUST NOT auto-adopt an attached gift into a wallet on arrival") for this second arrival path, because the same reasoning applies to it without change: accepting property, even through a page a visitor just told the confirmation prompt they recognize, is a decision a client must still surface as its own explicit second step, never folded into the moment a page happened to offer it. A later, separate, visitor-initiated Claim action — distinct from the confirmation above — is the only path that actually runs §5 step 1's full verification and adds the credential to the real wallet; a Dismiss action discards a pending offer without ever claiming it, a different outcome from either a class failing the whitelist or a confirmation being denied, since dismissal is what happens to something a visitor was found able to receive and chose not to keep.

**What this version still doesn't specify.** Nothing here lets any whitelisted class skip the sandbox straight into the live wallet for any domain, however well established a visitor's relationship with it already is — §3.8.3 gives that its own answer, a per-identity trusted-offer-domains list, rather than folding it into this section. Nor does this version say anything about letting a visitor preview a pending offer the way they'd inspect anything else already in the wallet before deciding whether to claim it — §3.8.4 gives that its own answer too. Neither changes what this section already specifies about the whitelist check, the confirmation prompt, the sandbox, or Claim/Dismiss themselves.

### 3.8.3 Wallet bridge — trusted offer domains

§3.8.2's own closing paragraph named this gap: nothing specified so far lets a repeat offer from a domain a visitor already trusts skip the confirmation prompt and the sandbox it requires every single time. This section is that capability, scoped as narrowly as the gap itself — a convenience a visitor grants one domain at a time, never a new class of access and never anything a domain or its page can request, set, or even detect on its own.

A conforming client maintains, per identity, a list of **trusted offer domains** — origins, not manifest classes or purposes, the same way a visitor trusts a store rather than a specific item it might sell them. Membership on this list changes nothing about what a domain is permitted to offer; §3.8.2's `policy.walletBridge.offer` whitelist still governs that completely, checked exactly as before. What membership changes is procedure, not permission: when an incoming `offerAsset` call names an `asset.class` already on that domain's own effective offer whitelist, **and** the requesting origin is on the visitor's trusted list for the active identity, a conforming client MAY skip both §3.8.2's confirmation prompt and its pending-offers sandbox — running the real credential verification immediately and adding the result straight to the wallet, with no human decision point in between. A domain that was never trusted, or an offer naming a class that domain's own manifest never whitelisted in the first place, behaves exactly as §3.8.2 already specified; nothing about this section changes either case.

This list is visitor-maintained, never domain-maintained. A conforming client MUST only ever add a domain to it through an explicit, visitor-initiated action taken on the client's own trusted confirmation surface — the same non-spoofable prompt §3.8.1 and §3.8.2 already require, extended with an opt-in control a visitor affirmatively activates on an ordinary (not-yet-trusted) offer, never a default, never something the requesting page can pre-check, submit, or otherwise influence from its side of that boundary. A client MUST also let a visitor list and revoke trust for any domain on it at any time, independent of whether that domain has ever actually sent another offer since — the same symmetry a client's other revocable client-side lists (a muted chat user, a blocked mail sender) already provide for the visitor's own earlier decisions.

**What this version still doesn't specify.** Preview-before-claim — letting a visitor inspect a pending offer's full asset before deciding whether to keep it — is given its own answer in §3.8.4, not this section; trust here only ever removes a prompt and a sandbox step for a domain the visitor has already decided they don't need either for, it doesn't change what either step shows when they do still apply.

### 3.8.4 Wallet bridge — previewing a pending offer

§3.8.2's own closing paragraph named this gap, restated unchanged by §3.8.3: nothing specified so far lets a visitor inspect a pending offer's full asset before deciding whether to claim it — only the name/class/quantity summary §3.8.2 already requires a pending offer's own card to show. This section closes it with no new wire format, no new page-visible capability, and nothing for a page to request, detect, or influence either way — the bridge itself is unchanged start to finish; this is entirely about what the client's own trusted UI, the same surface §11.2 already uses to list pending offers, lets a visitor do with one before acting on it.

A conforming client MAY let a visitor open a pending offer and inspect its underlying asset — name, class, quantity, and whatever other §5 asset fields the credential itself carries, including a thumbnail or model where the class has one — rendered the same way the client already renders anything already in the wallet. This changes nothing about either action a visitor still takes from there: Claim still runs §5 step 1's real verification and adds the credential to the wallet exactly as §3.8.2 specified, and Dismiss still discards the pending offer without ever claiming it, whether invoked from the preview or straight from the card. A client that offers no such preview, and only ever lets a visitor act on the summary §3.8.2 already requires a card to show, remains fully conforming — "MAY" here is deliberate: this section gives a visitor something extra to look at before the same two choices, not a new requirement layered on top of them.

**What this version still doesn't specify.** This was the second of the two gaps §3.8.2's own closing paragraph named — trusted offer domains (§3.8.3) and this — and closes the wallet-bridge capability as originally scoped by §3.8's own closing note: read, then sign, then offer, with sandboxing, trust, and now preview layered onto offer in turn. That isn't a claim the bridge is finished in some larger sense; any capability beyond read, sign, and offer was simply not yet asked for when this was written, not a gap this section or its predecessors ever named (§3.8.5 later adds a fourth, page-supplied preview).

### 3.8.5 Wallet bridge — previewing an asset from a page

§3.8.4 lets a visitor inspect an offer after it has been queued. This section covers the moment before that, and independent of it: a page that already holds a complete credential — typically one its own domain just minted, shown as a card on the page — asking the wallet to display that asset in the client's own preview surface while the visitor hovers or focuses the card, the way a client previews an item in a world. It adds no manifest field and nothing to the wallet's state.

A page requests a preview by handing the bridge the complete `domain-atlas-asset/1.0` credential (§5), and later asks for it to be hidden. The credential's `asset.class` is checked against the same effective `policy.walletBridge.offer` array §3.8.2 defined — a domain can preview exactly the kinds of asset it is allowed to offer, no more — with the same refusal posture as §3.8.1 and §3.8.2: a class not on the list is refused with no display, nothing a page can use to tell "not whitelisted" from "capability doesn't exist." The result is `{ allowed, shown }`; `shown` is true when the client displayed the preview.

No confirmation is required, because a preview is display-only: it queues nothing, signs nothing, adds nothing to the wallet and reads nothing from it. In exchange a conforming client MUST hold the display to three rules:

- **The client draws it, not the page.** The preview is rendered in a surface the page cannot script into or read, and every string the credential supplies (name, class, issuer, property keys and values) is shown as inert text, never interpreted as markup. Any image is a plain image reference and is never executed.
- **It is never presented as owned.** The preview MUST name the origin that requested it and MUST NOT suggest the asset is in the visitor's wallet or that its signature has been checked; a client MAY verify the credential first, but a page-supplied preview is otherwise unverified data.
- **A page cannot leave it up.** A preview ends when the page asks to hide it, when a later preview replaces it, or when the client's own inactivity limit lapses (the reference client uses 20 seconds unless the page re-requests it), so a page keeps one showing only by actively continuing to hover.

A client SHOULD place the preview where it places its own world previewer, honoring any dock position the visitor chose there. A client that offers no page previews remains fully conforming; a page treats `{ allowed: false }` and `{ allowed: true, shown: false }` alike as "no preview available."

**What this version still doesn't specify.** Previews of assets the visitor already holds, or of anything read back from the wallet, are not covered: this section only ever displays a credential the page itself supplied.

## 4. Rendering

Scenes render with WebXR directly in the browser, assets delivered as glTF over ordinary HTTPS — no plugin, no new codec, no new transport. This isn't a gap the protocol needs to fill: browser support for WebXR is already broad, and re-solving 3D delivery wasn't the point of this spec. §3.2's procedural fallback exists only for worlds that would rather describe a space in a few lines of JSON than author a 3D asset — the reference prototype's renderer is a deliberately dependency-free stand-in for what a production client does with WebXR and glTF directly.

## 5. Asset credentials (ownership)

An asset is a signed claim, not a database row. Any domain can verify it without a shared account system. One credential shape now covers both a one-of-a-kind collectible and a stackable quantity of raw material — what used to be two different credential types turned out to differ in exactly one respect that actually mattered, so this version says that difference with one field instead of with two parallel schemas:

```json
{
  "credential": "domain-atlas-asset/1.0",
  "id": "urn:atlas:asset:9f2a6e1c-9b3d-4a2e-8c31-1e6b2f0a7d44",
  "issuer": {
    "domain": "example.com",
    "publicKey": "base64url-ecdsa-p256-public-key"
  },
  "asset": {
    "name": "Bronze Compass",
    "class": "atlas.wearable",
    "model": "https://example.com/assets/compass.glb",
    "thumbnail": "https://example.com/assets/compass.png",
    "fungible": false,
    "presentation": "collectible",
    "properties": {
      "atlas.rarity": "common",
      "com.example.era": "Victorian"
    }
  },
  "owner": {
    "publicKey": "base64url-visitor-passkey-public-key"
  },
  "quantity": 1,
  "supersedes": null,
  "issuedAt": "2026-08-22T00:00:00Z",
  "signature": "base64url-signature-over-canonical-payload"
}
```

The issuer signs the canonical JSON of `{id, asset, owner, quantity, supersedes, issuedAt}`. Verification by any third domain requires no call back to the issuer:

1. Fetch the issuer's published signing key at `https://{issuer.domain}/.well-known/atlas-key.json` and confirm `issuer.publicKey` was valid at `issuedAt` (§5.3 covers why this is a small key history, not one key). This anchors trust in the same domain-ownership root as the manifest itself — whoever controls the domain controls the key, nothing else to bootstrap.
2. Verify `signature` over the canonical payload.
3. Challenge the visitor for a fresh WebAuthn assertion proving they currently hold the private key for `owner.publicKey`. This is what stops a copied credential file from being usable by anyone but the actual owner — possession of the JSON is not possession of the asset.
4. Confirm `id` isn't present on the issuer's revocation list (§5.3).

**On terminology.** This mechanism — a portable, cryptographically verifiable ownership claim independent of any platform — is the property NFTs were reaching for, without a token, a chain, or a gas fee. Keep the mechanism; don't borrow the vocabulary. A domain **issues** a credential, it doesn't "mint" one. A visitor **holds** an asset, they don't "own an NFT of" it. Calling this an open credential standard rather than a token scheme is both more accurate and doesn't drag in 2022's baggage by association.

**Three flags, one discipline** (`tradeScope` joins `fungible`/`presentation` as of v1.13 — see below). `asset.fungible`, `asset.presentation`, and `asset.tradeScope` are all fixed per `class` and all signed fresh by the issuer on every mint, split, consolidate, trade, or reissue of that class — never copied forward from an older credential of the same class. That's not an arbitrary rule; it's the same discipline `asset.properties` already needs for a fungible class (§5.1), stated here for three fields:

- **`fungible`** is the axis that decides how an asset moves. `false` — `quantity` is always exactly `1`, and the whole thing moves at once, whether that's an owner transferring it directly or the PvP transfer-on-loss mechanism §5.2 defines. `true` — `quantity` can be any positive integer, and only §5.4's split/consolidate mechanism (and §7's trading stations, built on the same mechanism) can validly turn one quantity into another. A class is one or the other, consistently, for every credential of it this issuer ever signs; nothing here supports a class that's sometimes stackable and sometimes not.
- **`presentation`** (`"collectible"` | `"document"`) has no effect on any of the above — it isn't a trust or behavior gate at all, only a signed hint for which panel a client shows the thing in (a shelf of collectibles vs. a stack of cards or papers). It's signed for the same reason `fungible` is: so a client can trust it exactly as much as it trusts everything else in `asset`, rather than needing a side channel or a guess.
- **`tradeScope`** (`"bound"` | `"local"`) says whether an asset can change hands at all, and if so, where. `"bound"` means never — no split, consolidate, trade, or drop (§5.5) into a world for someone else to take, this last one server-enforced as of v1.20 rather than left to a client's own goodwill; the asset is a relationship, not a good, and this is what keeps a relationship credential (a domain membership card, a Post Office or Trading Station membership) from ever becoming a tradeable item just because a trading mechanism happens to have gotten more general since it was minted. `"local"` — the default whenever a class doesn't set this field explicitly — is the status quo for everything already tradeable: transferable, but only ever finalized by the asset's OWN issuing domain, because that's a cryptographic necessity rather than a policy choice (only that domain holds the key needed to re-sign it). A future `"global"` value is reserved for an issuer declaring it's willing to finalize a trade whose counterparty or listing originated at a different venue (a federated station, say) — a statement about which venues the issuer trusts, never a grant of settlement authority to anyone but the issuer itself. Checked by a trading station immediately alongside `fungible` (§7): a `"bound"` asset is rejected with its own clear reason, not folded into the generic "not fungible" one.

### 5.1 Asset classes — interoperability without a central catalog

A credential proves *who owns what*, and now *how much*, and *whether it's one of many identical units or the only one of its kind*. It says nothing about whether the world the owner just walked into knows what to *do* with the thing — whether "Bronze Compass" should render as a wearable, sit on a shelf, or be ignored. That's what `asset.class` is for. A world declares which classes it recognizes (`policy.acceptedItemClasses`, §3); an asset outside that list still exists and is still verifiably owned, the world just has no defined behavior for it, and a well-behaved client falls back to an inert collectible rather than failing.

The classes are a namespace, not a catalog someone approves you into:

- **`atlas.*`** is reserved for a small, deliberately boring set of core classes published alongside this spec — `atlas.wearable`, `atlas.badge`, a handful of others — plus a reserved family for the fungible side of the same namespace: `atlas.element.*`, one entry per element on the periodic table (`atlas.element.iron`, `atlas.element.carbon`, `atlas.element.hydrogen`, …), a shared vocabulary that cost nothing to standardize because chemistry already agreed on it before this spec existed, with `atlas.currency` and `atlas.energy` alongside it for the non-elemental cases every economy still needs. All of it maintained the way Khronos maintains glTF's `KHR_*` prefix: a shared name nobody needs permission to use and nobody can be denied. (Earlier drafts, through v1.8, kept `atlas.element.*` and `atlas.currency` in a separate namespace from `atlas.wearable` and `atlas.badge`, because the credential shape itself had no field to say "how many" — a unique thing and a fungible one were different credential types by necessity. That split is gone; `class` is one namespace now, and `fungible` is what actually distinguishes a wearable from an ingot.)
- **Anything else uses reverse-domain naming** — `com.example.compass` — the same convention Java packages and Android use to avoid collisions. Any domain can mint a custom class with zero coordination; a class that turns out to be broadly useful is a candidate for eventual promotion into `atlas.*`.

This is closer to a MIME type registry than a marketplace: minimal shared vocabulary for the common cases, an open namespace for everything else, no single party who can reject an asset type.

`asset.properties` extends the same idea from *what kind of thing this is* down to *arbitrary facts about this particular class* — rarity, an era, a purity grade, anything a creator wants a class to carry. It's an open object, not a fixed schema: a domain can add a new key the moment it mints a new class, with no coordination and no registration, the same way it can mint a new `asset.class`. The same two-tier namespace applies — `atlas.*` for a small shared vocabulary worth standardizing (`atlas.rarity`, `atlas.purity`, and the like), reverse-domain keys (`com.example.era`) for everything a single creator invents on their own. `properties` is entirely optional and, being part of `asset`, is covered by the same signature as `name`, `class`, `fungible`, and `presentation` — a verifier that doesn't recognize a given key just doesn't render it, exactly as it already falls back gracefully on an unrecognized `asset.class`.

Two more `atlas.*` keys belong to that same shared vocabulary and need no schema change to exist: `atlas.serial` and `atlas.editionSize`, a pair a `fungible: false` credential's issuer can stamp on at mint time to say "this is instance N of an edition of size M" — a signed collector's-edition number, not a display convenience, since forging one without the issuer's key is exactly as hard as forging any other property. Both are strings for the same reason every other value in this catalog's example properties is a string rather than a number: `properties` has no numeric type of its own, and a verifier that only knows how to render text should never choke on a field it doesn't specifically understand. Whether an issuer actually enforces `atlas.editionSize` as a hard cap — refusing to mint instance M+1 of an edition of size M — is entirely an issuer-side policy question this spec has no opinion on, the same way it has no opinion on how an issuer decides what `atlas.rarity` to assign; what's standardized here is only the two keys' meaning to a client once they're present, not how an issuer arrives at the values it signs.

One constraint on `properties` isn't optional the way the rest of this paragraph is, and it applies only to a `fungible: true` class: `properties` has to be a function of `class`, not of the individual credential. An issuer attaches whatever properties that class carries every time it signs a new credential of it (mint, split, consolidate, trade), so two balances of the same class from the same issuer always carry identical properties by construction. That's what keeps §5.4.1's consolidation sound — consolidation merges same-class balances purely by summing `quantity`, and if two balances of "iron" could carry different purities, merging them would silently blend or discard a fact a holder might actually care about. A `fungible: false` class carries no such constraint: `properties` is a per-credential fact about one specific asset (this compass's condition, this exhibit's current description), free to differ from another asset of the same class and free to change over its life — which is exactly the case §5.1.1 covers next.

### 5.1.1 Reissue: state that changes after minting (non-fungible only)

An asset's `properties` bag is fixed at mint time because `asset` sits inside the signed payload — the only way to change a fact about it without invalidating the signature the whole credential rests on is to stop editing it and issue a new one instead. An asset credential carries one more field for exactly that, alongside `id`, `asset`, `owner`, and `quantity`:

```json
"supersedes": null
```

— `null` on an asset as originally minted, or the `id` of the asset credential this one replaces. This mechanism is scoped to `fungible: false` classes, and it's worth being explicit about why rather than leaving an implementer to assume it applies everywhere: §5.1's per-class `properties` constraint requires every `fungible: true` credential of a class to carry identical properties, precisely so §5.4.1's consolidation can sum quantities without silently blending a differing fact. Reissuing one balance's `properties` in place would break that invariant the moment it diverged from every other balance of the same class sitting in the same or a different wallet — so a `fungible: true` credential's properties only ever change at the class level (the issuer changing what a class carries going forward, which naturally applies to the next mint, split, or consolidation of it), never by reissuing one specific balance. A `fungible: false` asset was never claiming to be interchangeable with another asset of its class in the first place, so it carries none of that risk — a museum exhibit's info card changing after a visitor already picked it up is exactly the kind of per-instance fact this section exists for. Unlike §5.4.1's consolidation, `supersedes` here never takes the array form — there's nothing to consolidate; a `fungible: false` asset has exactly one predecessor or none.

A reissue is initiated by the issuer, not the holder — the same authority that could mint the asset in the first place is what's allowed to say its state changed, for the obvious reason that a holder rewriting their own asset's properties however they like would make the bag meaningless. The issuer signs a new credential with a fresh `id`, `owner` and `quantity` carried over unchanged (a reissue is not a transfer — that's §5.2's job — and quantity is always `1` here regardless), `asset` updated however the issuer's own logic determines (new `properties` values, typically; nothing stops `name` or `model` changing too, though `fungible` and `presentation` stay whatever the class always carries), and `supersedes` naming the `id` being replaced. It revokes the superseded `id` with `"reason": "superseded"` (§5.3) in the same act as signing the new one — the same atomicity guarantee §5.4 already gives a split or trade settlement: there is never a moment where both the old and new credential look simultaneously valid.

Verification of the new credential is unchanged — §5's four steps apply exactly as they do to a first-minted asset, and a stranger who's never seen the predecessor verifies it exactly the same way. What's different is only relevant to whoever already held the superseded `id`: their copy is now revoked, and somewhere out there is a live replacement instead of just a dead credential. How a client discovers that replacement is deliberately left unspecified here, the same way §5.3 leaves the transport for checking a revocation list unspecified — a client already has to notice a credential it holds turned up revoked; noticing that the revocation carries a named successor, and fetching that successor by whatever channel the issuer offers, is the same kind of client-side polling problem, not a new category of one. The one hard requirement, regardless of channel: a claimed replacement is never adopted on the strength of arriving over that channel alone — it goes through the exact same four-step verification as any other credential, `supersedes` included, before a client treats it as anything more than an unverified claim.

### 5.1.2 Class discovery — previewing a class before you hold one

§5.1's namespace already establishes that a class carries no approval gate; a domain choosing to *describe* one of its own classes publicly, before anyone has actually minted one, is the same voluntary disclosure §7's Catalog discovery already established for trading-station classes specifically — an issuer publishing more about its own class than this spec requires costs nothing, since the mint endpoint already hands out the identical data the moment anyone actually acquires one. A domain that offers this exposes a class-lookup read, keyed by `class`, returning that class's `name`, `model`, an optional `thumbnail`, its `fungible` and `presentation` flags, `tradeScope` (§7), and any `properties` it carries — every field a minted credential's own `asset` object would carry, resolved at the class level rather than the instance level. That's enough for a client to render a faithful preview of a class nobody at hand holds yet: a still-unopened crate, a stall's unclaimed wares, anything a world wants to show before a visitor acts on it, the same way a store window shows the item before it's bought rather than only after. A class this domain doesn't define returns a plain not-found response rather than a placeholder — this read only ever describes classes the issuer itself actually defines, never classes it merely knows the name of.

Unlike §7's Catalog discovery, this is deliberately unfiltered by `fungible` or `tradeScope` — it answers "what is this class" for any class the issuer defines, tradable or not, fungible or not, which is a strict superset of what a trading station's own catalog needs. That's also why it's specified here rather than folded into §7: a class doesn't need to be tradable, or even fungible, to be worth previewing before it's held, and tying the read to the trading-station section would wrongly imply the two are the same mechanism serving the same purpose. Same ungated "read is open" treatment as every other discovery read this spec already defines (Browsing and Catalog discovery, §7; the discovery directory, §3.3) — nothing this returns is a secret a client couldn't already learn one action later, by simply acquiring the class and reading its own signed `asset`.

### 5.2 Loadouts and consequence

This section covers the `fungible: false` side of an asset changing hands — putting a unique asset at risk inside a world, as distinct from an issuer updating its state (§5.1.1). A `fungible: true` balance doesn't load into combat the way a unique asset does; it moves by the arithmetic §5.4 defines instead, initiated by the owner and finalized by whoever holds issuing authority over it, never by a world's own rules deciding a quantity changed hands.

Owning an asset and putting it at risk inside one world are different acts, kept different on purpose — it's what makes visiting a `"pvp"` world safe to do at all without exposing an entire wallet everywhere a visitor goes.

- **Wallet** — everything a visitor holds a valid credential for. Always safe, regardless of which worlds they've visited.
- **Loadout** — the subset of the wallet presented into one world's active session (an "equip" action in the client, using the same per-presentation WebAuthn assertion already required above). Only loadout assets are ever subject to that world's rules.

A conforming client checks `profile.capabilities.combat` before letting a visitor load anything. If it isn't `"none"`, the client must show a real warning — *"assets you load here can be lost under this world's rules; anything left in your wallet stays safe"* — and refuses to load silently.

**Transfer on loss.** A world cannot unilaterally reassign an asset it didn't issue — if it could, any world could flip on `"combat": "pvp"` and help itself to visitors' portable belongings, quietly undoing everything above. Authority to transfer an asset stays with whoever holds its private key, full stop. What a PvP world's rules actually trigger is the *loser's own client* co-signing a transfer credential to the winner's public key, using the same key that already proved ownership — pre-authorized the moment the visitor chose to load that asset into a world they knew was flagged `"pvp"`. The world referees the event; the owner's key is what makes the transfer valid everywhere the asset travels next. No world, including the one where the loss happened, can produce a valid transfer for an asset it doesn't hold the key to. Net effect: the only new capability a hostile world gains is convincing an informed, consenting visitor to load an asset there — never a way to reach into anyone's wallet.

The transfer itself is a small, self-contained credential, signed by the loser's key using the proof mechanism §6.2 defines:

```json
{
  "credential": "domain-atlas-transfer/1.0",
  "itemId": "urn:atlas:asset:9f2a6e1c-9b3d-4a2e-8c31-1e6b2f0a7d44",
  "from": { "publicKey": "base64url-losers-passkey-public-key" },
  "to": { "publicKey": "base64url-winners-public-key" },
  "worldContext": { "domain": "example.com", "world": "arena" },
  "transferredAt": "2026-08-24T00:00:00Z",
  "proof": {
    "signerRole": "webauthn",
    "publicKey": "base64url-losers-passkey-public-key",
    "clientDataJSON": "base64url",
    "authenticatorData": "base64url",
    "signature": "base64url-der-ecdsa-signature"
  }
}
```

(`domain-atlas-transfer/1.0` and its `itemId` field keep their names from before this version — this is a separate credential type the item/resource merge didn't touch, and it only ever names a `fungible: false` asset's `id`, one whole unit moving at a time.)

`proof` covers `{itemId, from, to, worldContext, transferredAt}` under §6.2's mechanism. Anyone holding this credential — the winner, the world that refereed the loss, a third domain the asset later travels to — can verify it independently: recompute the payload hash, confirm `proof.publicKey` matches `itemId`'s currently-recorded owner (the same lookup §5 step 1 already does against the issuer's key), and verify the signature. `worldContext` exists so a verifier, or a later dispute, can see *which* world's rules the loss happened under without that fact needing to live anywhere else. This is not a new credential type competing with §5's asset credential — it's the event that changes an existing asset credential's `owner` field the next time that asset is re-issued or re-presented; a conforming implementation treats a verified transfer as authoritative over who `owner.publicKey` names for that `id` going forward, the same way a revocation (§5.3) is authoritative over whether an `id` is still valid at all.

### 5.3 Revocation and key rotation

An issuer publishes revocations alongside its signing key:

```json
// https://example.com/.well-known/atlas-revocations.json
{
  "revoked": [
    { "id": "urn:atlas:asset:9f2a6e1c-9b3d-4a2e-8c31-1e6b2f0a7d44", "revokedAt": "2026-09-01T00:00:00Z", "reason": "refunded" }
  ]
}
```

`reason` (`"refunded"` | `"duplicate-exploit"` | `"compromised-key"` | `"issuer-request"` | `"superseded"` | `"consolidated"`) is informational; revoked is revoked regardless of why. `"superseded"` marks a credential replaced by a newer one issued from it — a `fungible: false` asset reissued with updated state (§5.1.1), or a `fungible: true` balance replaced by a split's remainder or a trade's settlement (§5.4); either way, `supersedes` on the new credential names the `id` this reason was recorded against. `"consolidated"` is the same idea for the opposite direction, and only ever applies to a `fungible: true` class: several balances revoked at once because one new balance now replaces all of them together (§5.4's `supersedes` array). Clients cache this list the way they cache the manifest, short TTL — checking a wallet against it shouldn't mean a network round trip per asset on every portal crossing.

**One spend per credential.** An operation that spends a credential (redeem, transfer, reissue, split, consolidate, convert, purchase, fulfil, export to a file, and the trade and drop settlements) is check, then sign or mint, then revoke. An issuer MUST make that exclusive per credential: when several requests spend the same credential at once, exactly one succeeds and the others are refused as already spent. An implementation takes a lock on the credential before checking it and holds it until the revocation is written; it does not need to be visible on the wire, and a request that cannot get the lock in reasonable time is refused as busy rather than waiting forever.

Key rotation is the sharper edge of the same problem: a single signing key with no history means a compromise leaves no way to tell a credential the real owner signed from one forged afterward. So `atlas-key.json` holds a small history instead of one key:

```json
// https://example.com/.well-known/atlas-key.json
{
  "keys": [
    { "publicKey": "base64url-current-key", "validFrom": "2026-08-01T00:00:00Z", "validUntil": null },
    { "publicKey": "base64url-old-key", "validFrom": "2025-01-01T00:00:00Z", "validUntil": "2026-08-01T00:00:00Z" }
  ]
}
```

An asset issued last year under a since-rotated key still checks out, because verification confirms the key was valid *at `issuedAt`*, not that it's current. A genuine compromise is handled by both mechanisms together: rotate immediately (close the compromised key's `validUntil`) to stop new forgeries, then revoke by `id` any credential issued during the suspected compromise window. Rotation limits future damage; revocation cleans up what already happened.

### 5.3.1 Concurrent keys

The example above shows sequential rotation — one key's `validUntil` meeting the next one's `validFrom` exactly — because that's the common case, but nothing about verification (§5 step 1: was this key valid at `issuedAt`) actually requires the entries in `keys` to be exclusive. Two or more can be valid at once. That's an intentional capacity of the schema, not an accident of it, even though nothing before this version ever said so — worth stating plainly rather than leaving an implementer to assume the opposite and write a verifier that breaks the moment two entries are valid at the same time.

A domain has two distinct reasons to want this:

**Redundancy and delegation** — more than one key valid for the *same* purpose at once, so no single key is a single point of failure. A domain might run issuance from two independent servers, each holding its own key, so rotating or losing one doesn't halt the other; or delegate issuance to a partner team or vendor under a key that's entirely separate from its own, revocable on its own schedule without touching anything else:

```json
{
  "keys": [
    { "publicKey": "base64url-primary-issuer-key", "validFrom": "2026-01-01T00:00:00Z", "validUntil": null, "label": "primary issuer" },
    { "publicKey": "base64url-partner-issuer-key", "validFrom": "2026-06-01T00:00:00Z", "validUntil": null, "label": "partner: example-vendor" }
  ]
}
```

`label` is optional and purely informational — a human-readable note for whoever's reading the document, the same non-enforced advertisement role `profile` and `policy` fields already play elsewhere (§3.4). A verifier ignores it entirely; nothing about credential verification changes for having it.

**Purpose separation** — a different key for a different job, rather than one key stretched across everything a domain signs. §3.7's manifest identity signature and §5's asset issuance never had to share a key; a domain can publish one key it only ever uses to sign its manifest and a separate one it only ever uses to sign assets, both living in the same `atlas-key.json`. Nothing in the document itself needs to say which entry is for which purpose — purpose is always declared by whoever's *using* the key, never by the key document: a manifest names its own `identityKey` (§3.7), an asset credential names its own `issuer.publicKey` (§5). `atlas-key.json` only ever answers one question, for any number of concurrent keys or purposes behind it — was this specific key valid at this specific moment.

**Revocation and rotation stay per-key.** If one of several concurrent keys is compromised, closing its `validUntil` and revoking credentials issued under it during the compromise window (the existing procedure above) doesn't touch any other currently-valid key. Each entry's history is independent, the same way each asset's revocation is independent of every other asset's.

### 5.4 Splitting and consolidating fungible balances

A `fungible: false` asset (§5.2) only ever needs the owner's own key again — that's the whole point, nobody but the owner can move it. Raw materials, fuel, currency don't fit that shape: nobody wants a separate signed file for each of the 47 units of iron someone's carrying, and giving a friend 10 of them shouldn't require getting a whole new asset issued from scratch. A `fungible: true` asset's `quantity` is what makes that possible — the same credential shape §5 already defines, just splittable and combinable in a way a `fungible: false` one deliberately isn't:

```json
{
  "credential": "domain-atlas-asset/1.0",
  "id": "urn:atlas:asset:9f2a6e1c-9b3d-4a2e-8c31-1e6b2f0a7d44",
  "issuer": {
    "domain": "example.com",
    "publicKey": "base64url-ecdsa-p256-public-key"
  },
  "asset": {
    "name": "Iron (Fe)",
    "class": "atlas.element.iron",
    "model": "https://example.com/assets/iron-ingot.glb",
    "thumbnail": "https://example.com/assets/iron-ingot.png",
    "fungible": true,
    "presentation": "collectible",
    "properties": {
      "atlas.purity": "99.9%"
    }
  },
  "owner": {
    "publicKey": "base64url-visitor-passkey-public-key"
  },
  "quantity": 47,
  "supersedes": null,
  "issuedAt": "2026-08-22T00:00:00Z",
  "signature": "base64url-signature-over-canonical-payload"
}
```

Verification is the same four steps as §5, plus one gate before any operation in this section runs at all: a verifier — most concretely, the issuer endpoint honoring a split, consolidate, or trade request — must confirm `asset.fungible === true` on every credential it's asked to split, consolidate, or fold into a trade, and refuse with a clear error otherwise. §5.1 already covers why: a `fungible: false` credential's `quantity` is definitionally `1`, and there is nothing for this section's arithmetic to do to it.

`supersedes` names the `id`(s) of the credential this one replaces: `null` for a first issuance, a single `id` for the common case of one balance becoming one new balance (a split's remainder, a trade settlement), or an array of ids when several balances are consolidated into this one (§5.4.1). Whichever shape it takes, the issuer revokes every named old `id` — `"reason": "superseded"` for the single-id case, `"consolidated"` for the array case (§5.3) — in the same act as signing the new one, so there's never a moment where two conflicting balances both look valid.

**Why a balance instead of a key alone.** This is a real trade-off against §5.2's independence, not an oversight. A `fungible: false` asset's owner can move it forever without the issuer's involvement, because there's nothing to split — the whole thing moves or it doesn't. A `fungible: true` balance has to be splittable (give away 10 of 47) and combinable (two balances of the same class becoming one), and only whoever is authorized to sign a new number can do that arithmetic validly — the owner's key alone can't turn a valid "47" into a valid "37," any more than a person can validly rewrite their own bank balance. So changing a fungible balance's quantity is initiated by the owner (their WebAuthn assertion authorizes the request, the same challenge-response as issuance in §6) but finalized by whichever domain currently holds issuing authority over that balance — starting with the original issuer, and reassignable, as §7 covers next, to a trading station for the moment a trade actually clears.

#### 5.4.1 Consolidating balances

The combinable half of the trade-off above, made concrete: a wallet accumulates separate `fungible: true` balances of the same `class` over time (minted twice, received as a split's remainder and separately as a gift, and so on), and nothing about holding several of them separately is wrong — each verifies independently. Consolidating them into one is a convenience, not a correctness requirement, and it's bound by the same rule as splitting: only whoever finalizes credentials for that balance can validly produce the merged total, so this is issuer-mediated the same way a split is, not something a wallet can do to its own records unilaterally.

A consolidation request names two or more balances that all share the same `class`, the same `issuer`, and the same `owner.publicKey` — a domain has no basis to merge balances across different owners, and merging across classes or issuers isn't merging at all. Every named balance must also carry `asset.fungible === true`; the issuer verifies each one the same way it would before honoring a split (signature checks out, not already revoked, owner matches, fungible), sums their `quantity`, and signs one new balance for the total, with `supersedes` set to the array of every id it replaces. The old balances are revoked with `"reason": "consolidated"` (§5.3) only once the new balance has been signed, so a failure partway through never leaves a wallet with both an unmerged balance and no merged one to replace it.

### 5.5 World drops — leaving an asset for anyone to find

Every transfer mechanism this document has defined so far is a direct handoff: a trade names a counterparty or an open listing a specific claimant matches against (§7), a gift attaches a credential to an addressed mail message (§11.2), consolidation and splitting stay with the same owner. None of them describe a visitor simply setting something down in a world for whoever happens to walk by — no addressee, no negotiation, just "this is here now, take it if you want it." This section defines that mechanism.

A drop is hosted by whichever domain's world it's dropped into (the *hosting domain*), not necessarily the domain that issued the credential being dropped — an asset picked up in one world, carried to another, and left there is an ordinary, fully-supported case, not an edge case bolted on afterward. The hosting domain exposes three actions:

1. **Drop.** The current owner submits the full signed credential, the world identifier (an opaque string scoped to the hosting domain — this spec has no independent concept of what worlds exist or their policy; see §10), a renderer-native position, and a signed intent (§6.2) authorizing the drop. The hosting domain verifies the credential exactly as any verifier would (§5's four steps, fetching the issuer's own published key when the issuer isn't itself — see §5 step 1), rejects `asset.tradeScope === "bound"` outright (§5, "Three flags, one discipline"), and — the one deliberate omission — does not require `asset.fungible === true` and does not look at `quantity` at all, unlike every other transfer mechanism in this spec. A drop always hands over a credential whole; a visitor who wants to leave only part of a fungible balance splits it first (§5.4) into a new balance of exactly that amount, then drops that. Once accepted, the credential is recorded as a live drop and the hosting domain returns an opaque drop id.
2. **List.** Anyone may ask a hosting domain what's currently dropped in a given world. This is deliberately open, unauthenticated read access — the same asymmetry §7's own listings and §11.3's inbox-check already establish for their respective read paths — because a drop sitting in a world is already visible to anyone physically present there; exposing it over an API reveals nothing a client couldn't already render by standing in the scene.
3. **Claim.** Anyone presents a signed intent (§6.2) naming a drop id. The hosting domain settles this as a reservation, not a lookup: the drop record is removed from its store as the very first step, before anything else happens, and whichever concurrent claim actually performs that removal is the one that wins — a losing concurrent claim for the same id gets a plain "already gone" rejection, the same experience as reaching for something someone else picked up a moment earlier. There is no special case for reclaiming a drop the claimant made themselves; every claim, without exception, is fulfilled by revoking the dropped credential and minting a fresh one naming the claimant as owner (§5.3) — the same real transfer-of-custody primitive this spec already uses for trade settlement and consolidation, because a dropped item was never in ownership limbo while it sat in the world.

**Cross-domain claims.** If the hosting domain also issued the dropped credential, it fulfills the claim directly — minting and revoking are both its own to do. If a different domain issued it, the hosting domain cannot legitimately re-sign someone else's credential; only the actual issuer holds that signing key. So instead, the hosting domain relays the claim to the issuing domain, exactly the way §11.4 already relays mail to a recipient's home domain: it signs a small attestation of its own — naming itself, the drop id, and the claimant's public key — with the same key `.well-known/atlas-key.json` already publishes, and sends it alongside the original credential. The issuing domain fetches the hosting domain's published key, verifies the attestation against it (the identical cross-domain trust bootstrap §5 step 1 and §11.4 step 3 both already rely on, no new discovery mechanism), confirms the credential hasn't already been revoked, and — once satisfied — performs the actual mint-and-revoke itself, returning the freshly-minted credential back through the hosting domain to the claimant. This is the second use of the relay-attestation pattern §11.4 introduced, not a new one: a domain vouching for a fact to a domain that has no other way to observe it directly.

**What's client-enforced vs. server-enforced.** A world's own policy — whether it accepts drops at all (`policy.itemDropsAllowed`), which classes it renders (`policy.acceptedItemClasses`), whose issuers it trusts (`policy.trustedIssuers`) — lives entirely in the manifest (§3.4) and is enforced by the client, the same split of responsibility every other manifest-declared policy field in this spec already has (§3.4.1); the hosting domain's own server has no notion of "worlds" beyond the opaque identifier it's handed, and enforces only what's actually a fact about the credential itself (ownership, signature, revocation, `tradeScope`). A client that renders a drop its own world policy would have refused is a client bug, not a protocol violation — the same posture §3's policy fields already take everywhere else.

### 5.6 Direct transfer

Every transfer mechanism above assumes a specific context: §5.2 needs a world refereeing a loss, §5.4/§7 needs a matched counterparty or an open listing, §5.5 needs a location to leave something in and a claimant to walk up and find it. None of these fit the plainest case a real relationship between two identities actually needs: "I hold this, send it straight to that public key, nothing wanted back, no world or station involved at all." This section defines that.

The current owner submits the full signed credential, the recipient's public key, and a signed intent (§6.2) authorizing exactly that move:

```json
{
  "credential": { "...": "the full domain-atlas-asset/1.0 credential currently held" },
  "recipientPublicKey": "base64url-recipients-public-key",
  "intent": {
    "payload": { "credentialId": "urn:atlas:asset:9f2a6e1c-9b3d-4a2e-8c31-1e6b2f0a7d44", "recipientPublicKey": "base64url-recipients-public-key", "action": "transfer" },
    "proof": { "signerRole": "raw-ecdsa", "publicKey": "base64url-current-owners-public-key", "signature": "base64url" }
  }
}
```

The issuing domain verifies the presented credential exactly as any verifier would (§5's four steps), confirms `intent.proof`'s public key matches `credential.owner.publicKey` — the same ownership check every other transfer mechanism in this spec already makes — and rejects `asset.tradeScope === "bound"` outright, the same discipline §5's "Three flags, one discipline" note and §5.5's Drop step both already apply. `asset.fungible` is required to be `false`; a fungible balance moves by §5.4's split-then-hand-off arithmetic instead, not by this mechanism, at least for now. A self-transfer (a recipient equal to the current owner) is rejected outright — there is nothing for it to accomplish. Once authorized, the domain revokes the presented credential (§5.3, reason `"transferred"`) and mints a fresh one naming the recipient as owner, in the same atomic revoke-then-mint act §5.5's Claim step and §7's Settle step already use — the actual instance (a serial number, any rolled properties) survives the move, never re-derived fresh from the class's static definition.

Unlike §5.2's loadout transfer, this is not a separate credential type and needs no world, no passkey ceremony tied to a `worldContext`, and no refereeing party at all — it is the plain §5 asset credential, moved by nothing more than its own current owner's signature over exactly what that signature authorizes. Unlike §7's Trading Station, no membership is required and no counter-offer is matched; unlike §5.5's World Drops, there is no location and no anonymous claimant, only a named recipient whose public key the sender already knows.

### 5.7 Redemption

Giving an asset away (§5.6) and giving it up entirely are different acts. A holder who is simply done with something — a spent coupon, a membership they no longer want — has no recipient to name at all, and forcing one onto the wire would misrepresent what's actually happening. This section defines the plain revocation-by-request an owner may make of their own credential:

```json
{
  "credential": { "...": "the full domain-atlas-asset/1.0 credential currently held" },
  "intent": {
    "payload": { "credentialId": "urn:atlas:asset:9f2a6e1c-9b3d-4a2e-8c31-1e6b2f0a7d44", "action": "redeem" },
    "proof": { "signerRole": "raw-ecdsa", "publicKey": "base64url-current-owners-public-key", "signature": "base64url" }
  }
}
```

Verification follows the same ownership-and-signature discipline §5.6 uses, with one deliberate difference: `asset.tradeScope === "bound"` is not rejected here. A bound relationship credential (a domain, Post Office, or Trading Station membership) can never be handed to someone else (§5, "Three flags, one discipline"), but its own holder relinquishing it entirely raises no question of who would receive it, so `tradeScope` is never checked for this action. `asset.fungible` is still required to be `false`, the same "no quantity to negotiate" scope every other single-credential action in this section shares. Once authorized, the domain revokes the presented credential (§5.3) with reason `"issuer-request"` — from the protocol's own point of view this is still the issuer revoking, exactly as §5.3 has always described revocation as an act the issuer publishes, never one a holder can perform directly — just reached through a route that treats the holder's own signature as sufficient grounds, the same discretion a domain always has over what counts as grounds for its own `"issuer-request"` entries.

### 5.8 Purchasing with a balance

Every mechanism above moves a credential that already exists: a whole unit (§5.2, §5.6), part of a balance kept by the same owner (§5.4), or a credential given up entirely (§5.7). None of them cover acquiring something NEW by spending part of what a visitor already holds — a plain purchase, the same shape whether what's being sold is a line on a menu, an item in a spatial world's shop, or anything else a domain decides to price this way. This section defines that mechanism, deliberately without naming what's being sold: nothing here is specific to any one kind of good, the same way §5.4's splitting arithmetic has no idea whether the balance it's splitting is currency, fuel, or raw material.

A domain opts a class into being purchasable by declaring, alongside its ordinary catalog fields, what it costs — a class to pay in and an amount of it:

```json
{
  "class": "com.example.market.lantern",
  "purchase": { "priceClass": "com.example.credit.balance", "priceAmount": 10 }
}
```

To buy it, the current owner of a balance of `priceClass` submits that balance, the class they want, an optional quantity (default `1`), and a signed intent (§6.2) authorizing exactly that:

```json
{
  "credential": { "...": "the full domain-atlas-asset/1.0 balance credential currently held" },
  "purchasedClass": "com.example.market.lantern",
  "quantity": 1,
  "intent": {
    "payload": { "credentialId": "urn:atlas:asset:9f2a6e1c-9b3d-4a2e-8c31-1e6b2f0a7d44", "purchasedClass": "com.example.market.lantern", "quantity": 1, "action": "purchase" },
    "proof": { "signerRole": "raw-ecdsa", "publicKey": "base64url-buyers-public-key", "signature": "base64url" }
  }
}
```

The issuing domain confirms `purchasedClass` is actually for sale (a catalog entry carrying its own `purchase` field — a buyer can never name an amount or a price of their own; both come from the catalog alone), computes the total as `priceAmount × quantity`, and verifies the presented credential the same way §5.4 verifies one for splitting — signature checks out, not revoked, owned by the signer, `asset.class` matches `priceClass`, `asset.fungible === true`, and `quantity` at least the total — with one deliberate difference from §5.4's own check: `asset.tradeScope === "bound"` is **not** rejected here. Spending a balance down has no recipient to reason about, the same logic §5.7 already applies to redeeming a bound credential outright; a domain may reasonably mint spendable balances that are bound precisely so they can only ever be spent, never gifted or traded away, and this is the mechanism that has to still work on one. A non-fungible `purchasedClass` (`asset.fungible === false`) may only be bought in `quantity: 1` — the same "there is no quantity to negotiate on a unique asset" rule every fungible/non-fungible split in this spec already enforces.

Once authorized, the purchased class is minted fresh (§5, built from the catalog exactly as any other new mint is) BEFORE the presented balance is touched at all — if the purchased class turns out to be unavailable for any reason (sold out, if it also declares a supply cap), nothing about the buyer's balance changes. Only once the purchase mints successfully does the domain debit the presented balance: the full amount if it exactly covers the total, or a fresh remainder balance for what's left over, following §5.4's own split arithmetic and revocation (`"superseded"`) exactly. The response carries both results — the remaining balance (or nothing, if it was spent to the exact amount) and the newly minted purchase — so a client never has to infer either from a partial response.

### 5.9 Fulfillment

A purchase (§5.8) — or any credential a domain issues meaning "present this once to receive something in the physical or in-world sense" — needs a closing act distinct from everything §5 has defined so far: every mechanism up to this point changes who holds a credential, never whether whatever it represents has actually been handed over. This section defines that closing act.

The domain operator submits the exact credential being presented, authenticated as the domain operator, not as any visitor, following §11.1's and §12.2's exact precedent: this spec takes no position on how a domain authenticates its own operator for this call, only on the shape of the request and what it does once authenticated. The domain confirms the credential is genuinely its own (signature checks out, `asset.fungible === false`, not already revoked) and revokes it (§5.3) with a new reason code, `"fulfilled"`. Unlike §5.7's redemption, there is no ownership check against the caller at all — the operator isn't claiming to be the credential's owner, only attesting that whatever it represents has been handed over to whoever presented it, the same authority an operator already has to revoke anything outright (§5.3) but exercised here through a route built specifically for this one act, and requiring the credential itself rather than a bare id, so the fulfillment can't be recorded against a credential the operator never actually saw presented.

`"fulfilled"` and `"issuer-request"` (§5.7) end a credential's life through the identical revocation mechanism, distinguished only by who was authorized to ask for it and why a client reading the revocation list would want to tell them apart — a holder relinquishing something voluntarily reads very differently from an operator confirming a hand-over actually took place, even though both are, structurally, just another entry in the same list §5.3 has always kept.

### 5.10 Time-based expiry

§5.3's revocation list answers "has anyone said this credential is no longer valid" — an explicit act, published once, checked ever after. It has no answer for "this was only ever meant to be valid for a while," a genuinely different shape of invalidity: nobody needs to *decide* a day pass stopped working at midnight, it just did, the moment the clock passed a deadline that was already known at the moment the pass was issued. This section defines that second, orthogonal mechanism.

A domain opts a class into self-expiry by declaring, alongside its ordinary catalog fields, how long a credential of it stays valid from the moment it's minted:

```json
{
  "class": "com.example.event.ticket",
  "expiresInMinutes": 240
}
```

Every credential minted of that class — first issuance, or a fresh mint following a split, consolidation, trade, purchase (§5.8), or reissue (§5.1.1) — carries a signed deadline computed from that mint's own clock:

```json
"asset": {
  "name": "Day Ticket",
  "class": "com.example.event.ticket",
  "fungible": false,
  "presentation": "document",
  "expiresAt": "2026-08-22T04:00:00Z"
}
```

`expiresAt` sits inside `asset`, so it's covered by the exact same signature every other asset-level field already is — a holder cannot extend, shorten, or remove their own deadline without invalidating the whole credential. It is absent entirely from a class that never declares `expiresInMinutes`; a client and a verifying domain alike treat a missing `expiresAt` as "never expires this way," never as "already expired," so every class this spec defined before v1.25 is completely unaffected. A re-mint gets a brand new deadline computed fresh, the same "never copied forward from an older credential" discipline `asset.fungible`/`presentation`/`tradeScope` already follow (§5) — there is deliberately no concept of a countdown surviving a split, consolidation, or purchase-driven remainder carrying an old balance's remaining time forward; each new credential's own clock starts the moment it's minted.

Checking `expiresAt` is exactly as cheap as it is to compute: compare it against the current time, no fetch, no list, no round trip to anywhere — unlike revocation, which needs the issuer's own published ledger (or, for a foreign credential, that credential's own issuing domain's ledger, §5's step 4 as extended for cross-domain checks), an expiry deadline already travels inside the credential a verifier is holding. Every §5 mechanism that already rejects a revoked `id` — splitting and consolidating (§5.4), direct transfer (§5.6), redemption (§5.7), spending a balance via purchase (§5.8), and fulfillment (§5.9) — rejects an expired credential the identical way, with its own clear reason rather than folded into a generic one. A credential that has expired was never revoked in the §5.3 sense at all: it carries no revocation-list entry, and a domain operator attempting to fulfill one after its own deadline passed gets rejected for having expired, not for having been revoked, even though the practical outcome — the credential can no longer be presented for anything — is identical either way.

The worked example is a spatial world's own ticket booth: a museum sells a `com.example.museum.ticket`-shaped class (this reference implementation's own is `atlas.demo.museum.ticket`) priced in an ordinary spendable balance (§5.8) and declaring its own `expiresInMinutes`, admitted once at the door via §5.9's fulfillment exactly like any other purchased, single-use credential. Nothing about §5.8's purchase endpoint or §5.9's fulfillment endpoint gained any ticket-specific logic to support this — a catalog entry declaring a price and a catalog entry declaring an expiry duration are both just fields on the same class, checked by mechanisms that already existed.

### 5.11 Third-party attestations

Everything through §5.10 answers questions about ONE domain's own claim — the issuer minted it, the issuer revokes or expires it, the issuer alone can reissue it. This section is different in kind: it lets a SECOND domain, one with no part in issuing an asset at all, publish its own signed opinion about that asset — an independent review, a certification, a standing check — without needing the asset's own issuer to cooperate, grant custody, or even know the attestation exists.

Nothing here needs new cryptography. It reuses the identical trust bootstrap this spec already establishes twice over: §11.4's relaying domain signs its own attestation with the key its `.well-known/atlas-key.json` publishes, and the home domain fetches that key independently to verify it; §5.5's cross-domain drop claim does the same thing to relay a claim back to an asset's real issuer. A third-party attestation is that same move, aimed at a new object instead of a relay hop:

```json
{
  "credential": "domain-atlas-attestation/1.0",
  "id": "urn:atlas:attestation:7e2a1c9d-4b3f-4e21-9c7a-2d8f6b1a0e33",
  "issuer": {
    "domain": "auditor.example",
    "publicKey": "base64url-ecdsa-p256-public-key"
  },
  "subject": {
    "assetId": "urn:atlas:asset:9f2a6e1c-9b3d-4a2e-8c31-1e6b2f0a7d44",
    "issuerDomain": "example.com"
  },
  "claim": "Reviewed on 2026-09-28 and found to be in order.",
  "issuedAt": "2026-09-28T00:00:00Z",
  "signature": "base64url-signature-over-canonical-payload"
}
```

`issuer` here is whoever is doing the attesting — a domain that need not have any relationship to `subject.issuerDomain`, the asset's actual issuer, at all. The issuer signs the canonical JSON of `{id, subject, claim, issuedAt}`. Verifying one is §5's own four steps, unchanged in substance, just aimed at the attesting domain instead of the asset's own issuer:

1. Fetch `https://{issuer.domain}/.well-known/atlas-key.json` — the ATTESTING domain's key, not the asset's own issuer's — and confirm it was valid at `issuedAt` (§5.3).
2. Verify `signature` over the canonical payload.
3. Confirm `id` isn't on the attesting domain's own revocation list (§5.3). An attestation is revoked by the domain that made it, on that domain's own schedule, entirely independent of whatever happens to the underlying asset — the asset could be traded, redeemed, or revoked by its own issuer without that touching the attestation's own validity at all, and vice versa.
4. Separately, and independently, a client that also cares whether the asset itself still checks out verifies `subject.assetId` the ordinary §5 way against `subject.issuerDomain`'s own key. An attestation's signature checking out proves only that the named domain really did make this exact claim about that exact asset id — it says nothing about whether the asset is still held, still valid, or exists at all. Neither check's outcome depends on the other's.

**What this deliberately doesn't require.** No relationship between the two domains — an asset's issuer never registers, approves, or is even aware that something else has been said about one of its assets. No custody — the attesting domain never holds the asset, never verifies anyone's current possession of it, and takes on no responsibility for it beyond the truth of its own signed statement. No shared registry, ledger, or aggregator — an attestation lives wherever its own issuer chooses to publish and stand behind it, discoverable by asking that domain directly, the same domain-local discovery §5.1.2 already establishes for class discovery. A client that wants to know everything ever said about a given asset still has to already know, or be told, which domains to ask — this spec doesn't invent a global index any more than it does anywhere else (§10).

**Deliberately out of scope: how a domain decides to issue one.** §5's own asset issuance is meant to be wide open — self-service onboarding is the entire point of that endpoint. Attestation is the opposite case: a domain signing its own reputation onto a claim about something it doesn't own is exactly the kind of act that should require real authentication of whoever's asking it to do so, the same posture this spec already takes toward domain-to-subscriber mail (§11.1) and manifest identity pinning (§3.7) — authenticated as the domain operator, not open to an arbitrary caller. This section specifies the credential shape and how any client verifies one; how a conforming domain authenticates and gates issuing one is exactly the domain-local operational policy §10 already leaves alone.

### 5.12 Clawback

Every mechanism through §5.11 changes custody at the request of whoever currently holds a credential — a transfer, a trade, a gift, even redemption is the holder's own act. This section is the one case where the issuer moves a credential without its current holder's consent at all: a fraud report comes in, an investigation confirms it, and the issuer revokes the credential wherever it now sits and mints a fresh one straight to whoever it actually belongs to, in the same act.

No new credential shape and no new verification steps — the fresh credential is an ordinary asset credential, checked by any client exactly as §5's four steps already describe. What's new is a second revocation reason code alongside `"transferred"` (§5.6): `"clawback"`, recorded against the OLD credential's id, distinguishing an issuer-forced recovery from a holder-authorized move the same way `"fulfilled"` (§5.9) already reads differently from a holder's own `"issuer-request"` redemption (§5.7). `asset.tradeScope === "bound"` is not checked here, deliberately — a relationship credential (a domain, Post Office, or Trading Station membership) is exactly as recoverable as anything else once forced back through the issuer's own authority, the same total reach §5.3's revocation has always had; `tradeScope` only ever disciplines what a *holder* may do with a credential, never what its own issuer can do to correct one.

Authenticated as the domain operator, not as any visitor or the credential's own holder, following §5.9's and §12.2's exact precedent: this spec takes no position on how a domain authenticates its own operator for this call, only on the shape of what it does once authenticated. This section defines no wire format at all for the request itself, only the resulting reason code and the mint-then-revoke ordering a conforming implementation should follow (new credential signed first, then the old one revoked — the same crash-safety ordering §5.4's split/consolidate and §5.5's claim already rely on).

**Deliberately out of scope: whether this was really theft, and how much of it.** This spec has no way to answer either question, and does not try to. A balance that's since been split, consolidated with legitimate funds, or spent partway is not something this mechanism traces or apportions — it recovers exactly the quantity named on the credential presented for clawback, no more. Which fraction of a mixed balance is actually tainted is a human investigation's conclusion to reach, using whatever audit trail (§5.1.1's `supersedes` chain, or a domain's own opt-in archive of superseded credentials) that investigation has available; this section only specifies what happens once that conclusion is acted on.

## 6. Identity

1. **Registration.** A visitor creates an identity once, client-side: `navigator.credentials.create()` (WebAuthn) generates a keypair in the device's authenticator. The private key never leaves secure hardware. The public key *is* the identity.
2. **No email in the protocol.** Email, if a client offers it at all, is a human-friendly recovery handle for linking a new device's passkey to an existing identity — out-of-band, client-side, never transmitted to a visited domain. A domain owner never sees a visitor's email through this protocol.
3. **Issuance.** When a world wants to grant an asset, it issues a WebAuthn challenge; the visitor's client signs it with the passkey, proving control of the public key the domain then binds the credential to (§5).
4. **Presentation.** Walking through a portal carries the wallet, not an account. Each world a visitor's assets are checked against re-verifies independently — there is no session to hand off, no SSO provider in the loop.
5. **Alternative: local-password identity.** WebAuthn assumes a platform authenticator or hardware key is available and that the visitor is comfortable with it — not universally true (older hardware, a locked-down environment, or simply a visitor who'd rather use a password they can carry in their head). A conforming client MAY offer a second identity mechanism for exactly this case: an ordinary ECDSA P-256 keypair, generated client-side the same as any WebAuthn keypair, but with its private key encrypted at rest under a password-derived AES-GCM key (PBKDF2, a high iteration count — the reference implementation uses 600,000, SHA-256) rather than held in secure hardware. "Unlocking" decrypts it into memory for the session; "locking" discards the decrypted copy without touching the encrypted one. This is a real, independent identity — not a stand-in for a missing passkey and not confined to testing — a visitor may pick it at onboarding instead of WebAuthn, and a client may let someone who has set up both switch which one currently answers to "self." It is deliberately a *weaker* mechanism, though, and a conforming client must not present it as equivalent: the private key exists, however briefly, as plaintext in the client's memory once unlocked, and the encrypted-at-rest copy is only as strong as the password protecting it — offline brute force against a stolen copy of that encrypted blob is a real threat model WebAuthn's hardware-bound key doesn't share. A client offering this option should say so plainly. Signing application data (§6.2) from a local-password identity uses the exact same canonicalize-then-sign shape as a WebAuthn identity, just without a WebAuthn ceremony to produce it — see §6.2's `"raw-ecdsa"` `signerRole` for the resulting proof envelope shape and its trust scope.

### 6.1 Wallet portability

The private key doesn't need a bespoke sync mechanism when it's WebAuthn-backed — passkeys already sync across a person's devices through the platform they're on (iCloud Keychain, Google Password Manager, cross-platform FIDO multi-device credentials), correctly a solved problem this spec has no business touching. A local-password identity (§6 step 5) has no such platform sync to lean on — its private key lives only in one client's encrypted local storage unless explicitly moved — so this spec defines a portable backup *format* for that case: an export wraps the raw keypair under an AES-GCM key derived from the password **and** a separately-generated recovery seed phrase combined (never either alone — the same "combine, don't check separately" reasoning §6.2 below applies to combining a hash of application data with other signed context, applied here to two secrets instead), shown to the visitor once at identity creation and never persisted anywhere. Losing the seed phrase doesn't lock a visitor out of their everyday, already-unlocked identity; it only forecloses ever producing a *new* portable backup of it without generating a fresh one.

What's left, for either identity mechanism, is syncing the *credentials* a wallet holds — and those aren't secret. A credential is a signed public claim; anyone can read one, and it's useless to anyone but its owner because presenting it still requires a live signature (a WebAuthn assertion, or a local-password identity's raw-ECDSA equivalent) only the private key can produce. That changes the shape of the problem: wallet sync needs no trusted channel, because nothing confidential moves through it. So rather than a sync protocol, this spec defines a portable export *format* — `atlas-wallet-export/1.0`, a plain JSON array of held asset credentials — and leaves the channel to the client: a browser's own account sync, a manual export, or whatever a future client invents. Any of them work, because the format is what needs to be shared, not the channel.

### 6.2 Signing application data

Presenting a credential (§6 step 4, §5 step 3) only ever needs to prove *possession* — a fresh assertion over a random, disposable challenge, discarded the moment it's checked. WebAuthn does that natively; there's no gap there. Co-signing a transfer (§5.2) and signing a trade intent (§7) need something stronger: a signature *over a specific payload*, one a third party can later hold up against that exact `itemId` or that exact `offer`/`want` pair and confirm it's what was actually signed — not just that the visitor's key was live at some moment. `navigator.credentials.get()` doesn't take arbitrary bytes to sign for that purpose; it takes a `challenge`, and the signature WebAuthn returns is over a fixed structure the authenticator builds itself (`authenticatorData || SHA-256(clientDataJSON)`), not over an application payload directly. A spec that just says "sign the payload" for a WebAuthn-bound key is describing something WebAuthn cannot do as stated.

The fix is standard practice wherever passkeys sign application data, not something invented here: set the `challenge` to a hash of the payload, and let the verifier walk the chain back.

1. **Canonicalize.** Serialize the payload object with sorted keys at every level, no insignificant whitespace, UTF-8 — the same deterministic form `signature` already presumes everywhere else in this spec (§5, §5.4), made explicit here because two independent implementations need to produce byte-identical output or nothing verifies.
2. **Hash.** `challenge = SHA-256(canonicalize(payload))`.
3. **Sign.** Call `navigator.credentials.get()` with that challenge. The authenticator returns `clientDataJSON` (which embeds the challenge, base64url-encoded), `authenticatorData`, and `signature` — a real assertion, not a workaround; this is the intended use of the `challenge` field, just with an application-defined hash in it instead of a server-issued nonce.
4. **Wrap.** Package the result as a **proof envelope**, attached to whatever it's proving:

```json
{
  "signerRole": "webauthn",
  "publicKey": "base64url-visitor-passkey-public-key",
  "clientDataJSON": "base64url",
  "authenticatorData": "base64url",
  "signature": "base64url-der-ecdsa-signature"
}
```

**Verification** reverses the steps: canonicalize the same payload, hash it, confirm that hash matches the `challenge` embedded in `clientDataJSON`, then verify `signature` over `authenticatorData || SHA-256(clientDataJSON)` against `publicKey` — P-256 assertion signatures are DER-encoded ASN.1, so a verifier written against raw `r‖s` ECDSA (as most non-WebAuthn crypto libraries expect) needs one small conversion step first. None of this is new trust; it's the existing WebAuthn ceremony, pointed at a payload instead of a bare nonce.

**A local-password identity (§6 step 5) signs the same canonicalized payload directly** — there's no authenticator to build a `clientDataJSON`/`authenticatorData` wrapper, so it just runs `ECDSA-sign(SHA-256(canonicalize(payload)))` with the decrypted raw private key and wraps the result more simply:

```json
{
  "signerRole": "raw-ecdsa",
  "publicKey": "base64url-visitor-public-key",
  "signature": "base64url-der-ecdsa-signature"
}
```

Verification is correspondingly simpler: canonicalize the same payload, hash it, and verify `signature` over that hash directly against `publicKey` — no `clientDataJSON`/`authenticatorData` indirection to unwrap, because there was never a hardware authenticator building one.

`signerRole` exists so a proof envelope names how it should be checked rather than a verifier having to guess. This spec defines two valid values for a real visitor's authority: `"webauthn"`, per above, for the primary hardware-backed identity §6 describes; and `"raw-ecdsa"`, for the explicitly lower-assurance local-password identity §6 step 5 allows a client to offer as an alternative — a conforming implementation MAY accept either as proof of a visitor's own authority, provided the public key it's checked against actually belongs to that visitor's currently active identity (whichever mechanism produced it), never as a substitute for verifying that binding. What a conforming implementation must never do is accept an *arbitrary* third `signerRole` value, or accept `"raw-ecdsa"` for a key that was never legitimately registered as somebody's own identity through §6 step 5 — that would reopen exactly the account-system dependency §6 exists to avoid. A test harness or reference client that needs to simulate a second visitor without a second physical authenticator or a real local-password identity (the reference implementation's "counterparty" identity, used only to demonstrate a two-party transfer or trade in a single browser tab) also produces a `"raw-ecdsa"` envelope the same way — structurally indistinguishable from a real local-password identity's, and that's fine: the trust boundary was never "which `signerRole` string appears," it's "does the public key being checked against actually belong to the party whose authority is being proven," which a conforming server-side implementation must establish itself (by requiring that key to already be on file as that visitor's registered identity, a membership's owner, or similar) rather than inferring from the envelope shape alone.

## 7. Trading stations

A trading station is nothing new architecturally — it's a world (§3), like any other, that a client can recognize by `profile.genre` as a venue for exchange. What's new is the swap itself: two visitors, who may be complete strangers from anywhere, need to trade without either one being able to walk away holding both sides — and without either one needing to already know who the other is, or be present at the same moment.

A station settles a balance **it itself issued** directly — both sides of a trade, offer and want alike, mint and revoke against this domain's own signing key the way §5.4 already describes. A balance issued by a *different* domain settles too, but only through that domain's own cooperation, and only when both domains have opted into trusting each other for exactly this: a station never mints a foreign class itself (it has no key that could legitimately do so), and a domain never lets a stranger's station direct what happens to one of its own credentials on a stranger's say-so alone. §9 explains why that second gate — not just the settlement mechanism below — is what actually makes this safe to offer, and why a purely mechanical fix for atomicity would not be.

**Trusted trade peers.** Each domain keeps its own list of other domains it treats as a genuine cross-domain trading counterpart — a short, operator-maintained allowlist, empty by default, checked in **both** of the two roles a trade can put a domain in: *(a)* as the station accepting a foreign-issued balance into a listing or a claim (the check already stated above, in §5.4's and this section's own presentation checks), and *(b)* as the issuer of a balance a *different* domain's station is relaying a lock or settle request against. One list, not two, because either role without the other is incomplete: a station that would accept anyone's foreign balance but never let anyone relay against its own credentials can list, but never settle, a foreign side; a domain that would honor any relay request but never accept a foreign balance back has nothing to offer a trade in return. Listing a domain here is a unilateral, domain-local decision (§10) — nothing in this protocol negotiates or confirms it is mutual — but it only accomplishes anything once both sides of a pair have each made the same choice about the other, the same opted-in-both-ways posture Post Office membership and Trading Station membership already require of a *visitor* (§11.3, above), applied here to a *domain*.

**Why this is the gate, not the lock below.** A two-phase lock/commit (next paragraph) guarantees a trade settles all-or-nothing across two domains — it says nothing at all about whether either domain *should* be trusted to be in the trade in the first place. Nothing stops a dishonest domain from minting unlimited fake value under a class name designed to look appealing and listing it at a station it doesn't control, in a trade matched atomically and correctly — atomically defrauding a stranger is still fraud. The trusted-peer allowlist is what keeps that scenario from ever reaching the lock/commit machinery at all: a foreign balance never enters a listing unless the station's own operator chose to trust that issuer, and a foreign relay request never touches a domain's own credentials unless that domain's own operator chose to trust the relaying station. The lock/commit mechanism below solves a real, separate problem — a network call can fail halfway through — but it is not, and was never meant to be, the answer to "should this domain be trading with that one at all."

**Cross-domain settlement.** When a listing's `offer` or `want` names a balance issued by a domain other than the station's own — and that domain is on the station's trusted-peer list (and, necessarily, lists the station's domain back, or none of what follows will succeed) — settling it is a two-phase **lock, then settle** against that domain's own `/atlas/trade/relay-lock` and `/atlas/trade/relay-settle` endpoints, rather than a local mint. Both phases use the same attestation-and-verify shape §11.4's federation relay and §5.5's cross-domain drop claim already establish: the relaying domain (the station orchestrating the trade) signs a small payload with its own key; the issuing domain fetches that key fresh from `/.well-known/atlas-key.json` and verifies it before acting, the same cross-domain trust bootstrap used everywhere else in this spec credentials cross a domain boundary.

*Lock* asks the issuing domain to suspend the named credential against this exact trade, before either side of the trade has mutated anything:

```json
{
  "credential": { "...": "the full balance credential being locked" },
  "attestation": {
    "relayingDomain": "station.example",
    "tradeId": "urn:atlas:trade:...",
    "credentialId": "same id as credential.id",
    "expiresAt": "2026-10-01T12:02:00Z"
  },
  "attestationSignature": "base64url"
}
```

A conforming issuer rejects a lock naming a credential it didn't itself issue, one already revoked or expired, or one already suspended for anything else (a different pending trade, or an unrelated administrative review) — and otherwise suspends it, the same mechanism §9's revocation-and-suspension infrastructure already provides, with `expiresAt` set a short, station-chosen duration out (on the order of two minutes). That short expiry is the whole of this mechanism's failure handling: there is no separate relay-unlock endpoint, because an abandoned or failed trade needs none — an expired suspension lifts itself, exactly as any other time-bounded suspension in this spec already does, the moment its own clock runs out.

*Settle*, called only once both sides' locks have succeeded, asks the issuing domain to actually spend the locked credential — a fresh balance minted for the counterparty (`spendQuantity` of it, or the whole thing for a unique asset) and any leftover minted back to the credential's own original owner, the same split-style arithmetic §5.4 already defines for a purely local trade:

```json
{
  "credential": { "...": "the same locked balance credential" },
  "attestation": {
    "relayingDomain": "station.example",
    "tradeId": "urn:atlas:trade:...",
    "credentialId": "same id as credential.id",
    "spendQuantity": 5,
    "newOwnerPublicKey": "base64url-the-counterpartys-public-key",
    "mailDeliverAttachedAsset": { "...": "optional, see Delivery below" }
  },
  "attestationSignature": "base64url"
}
```

A conforming issuer rejects a settle that doesn't name a credential currently locked for that exact `tradeId` — settle never runs ahead of, or instead of, a successful lock. Which of the trade's two sides needs locking and settling this way, and which settle locally, is decided independently per side: an all-local trade (both balances issued by the station's own domain) needs neither phase at all and settles exactly as it always has; a trade with one or both sides foreign-issued locks and settles only the foreign side(s), through whichever domain actually issued them.

**Delivery, revisited for the cross-domain case.** The Delivery paragraph below already covers the mechanism — a poster's remainder supersedes their old balance, and their received credential rides along as a mail attachment addressed to that same old id. What's new here is only *where* that received credential comes from: when the poster's own balance is locally issued, it's a fresh mint from this same settlement call, exactly as before; when the poster traded away a *foreign*-issued balance, the credential they're owed in return was minted by whichever domain issued the *other* side of the trade, and is carried into that foreign domain's own `relay-settle` call as `mailDeliverAttachedAsset` above — because only the domain that issued the id being superseded has a mail store the poster's own wallet is actually polling (§11's asset-update channel is addressed by issuer, not by station). The issuing domain verifies that attached credential against its own issuer's published key (the same foreign-credential check §5.5 already applies to a dropped item from elsewhere) before mailing it on the station's behalf — never on the relaying station's word alone. A visitor who wants to move a specific asset to a specific counterparty without any of this — no station, no allowlist, no lock/commit — still has §5.6's direct transfer for exactly that; this section's mechanism is an addition to it, not a replacement.

A trading station settles a fungible balance by matching class and quantity, the same mechanism §5.4 already defines — and it settles a specific unique (`fungible: false`) asset too, matched the same way but with `quantity` pinned to exactly `1`, since there's nothing to negotiate on a one-of-a-kind thing beyond which one it is. The two cases share one `offer`/`want` shape (`class` + `quantity` below) but settle differently: a fungible side mints fresh balances the way a split or consolidation already does (§5.4), while a unique side transfers the *actual presented instance* — the same specific asset, with whatever serial number, enchantments, or other per-instance state it already carried, not a fresh substitute freshly minted from the class's static definition. Nothing about `fungible: true`/`false` changes which trust properties apply; a station still can't produce either kind of settlement without a matching, signed intent from both sides. §5.6's owner-initiated whole-unit transfer remains available for two consenting parties who'd rather not go through a station at all — this section's mechanism is an addition to that, not a replacement for it.

This is the same problem real exchanges have always had to solve, and it doesn't need a blockchain to solve it — a station just needs to referee a trade the way §5.2 already has a world referee a PvP loss. A visitor posts a signed intent naming what they'll give and what they want, in an open listing anyone at the station can see; another visitor claims it by presenting a mirroring intent of their own; the station settles both sides together, atomically, so neither party can ever walk away holding both.

**The intent.** A visitor signs their own proposed trade with their own passkey — *"I'll give 10 `atlas.element.iron`, I want 5 `atlas.element.gold`, expiring at this time."* Nothing has moved yet; this is a signed offer, not a transfer. The intent itself is a small credential, signed the way §6.2 defines:

```json
{
  "credential": "domain-atlas-trade-intent/1.0",
  "offer": { "class": "atlas.element.iron", "quantity": 10 },
  "want": { "class": "atlas.element.gold", "quantity": 5 },
  "from": { "publicKey": "base64url-this-visitors-public-key" },
  "expiresAt": "2026-08-24T00:10:00Z",
  "proof": {
    "signerRole": "webauthn",
    "publicKey": "base64url-this-visitors-public-key",
    "clientDataJSON": "base64url",
    "authenticatorData": "base64url",
    "signature": "base64url-der-ecdsa-signature"
  }
}
```

`proof` covers `{offer, want, from, expiresAt}`, plus `counterparty` on a claim (below), when it's present. A visitor presents this intent alongside whatever `offer` actually is: a fungible balance (§5.4) sufficient to cover its `quantity`, or — when `offer.quantity` is `1` and the named class is non-fungible — the specific unique asset instance itself. Either way the station confirms `asset.tradeScope !== "bound"` and rejects the trade otherwise; for a fungible offer it additionally confirms `asset.fungible === true` and a sufficient balance, the same check §5.4 already requires before honoring any split or consolidation, while for a unique offer it confirms `asset.fungible === false`, that the presented instance's class matches, and that the presenter is its current owner. The station verifies this independently before any match or settlement, the same possession check §5 step 3 already requires for any other presentation — against its own published key when the credential's issuer is this domain, or against the issuing domain's own published key (the same foreign-credential check §5.5 already applies to a dropped item from elsewhere) when it isn't. A foreign-issued credential is accepted only when its issuer is on this station's own trusted-peer list (above); anything else is rejected outright, not relayed anywhere.

**Posting.** A visitor submits their own signed intent plus their own presented balance to the station on its own — no counterparty named, since an open listing doesn't have one yet — alongside a **Trading Station membership** credential (`atlas.tradingstation.membership`, `tradeScope: "bound"`, issued the same one-click way a Post Office membership already is, §11.3) — holding one is what a station requires before it's willing to hold a listing at all, the same abuse-scoping reasoning §11.3 already gives Post Office's own membership gate. Posting never settles anything by itself; it only queues, holding the listing — and the balance presented alongside it — until either a claim arrives or `expiresAt` passes.

**Browsing.** A station exposes its own current open, unexpired listings for anyone to read — no membership required for this part, since browsing commits to nothing and reveals nothing a listing's own poster didn't already choose to make public by posting it (the same "read is open, write is gated" asymmetry §11.3 already gives Post Office's inbox-check versus its send). Each listing carries enough for a prospective buyer to decide and act: its id, the poster's public key, `offer`, `want`, and `expiresAt`. A station MAY omit a listing that's already expired rather than waiting for a client to notice, but MUST NOT return one that's already been claimed — once claimed, a listing is gone, settled and left with no residue.

**Catalog discovery.** Posting a listing means naming a `want`, and naming a `want` means already knowing what a station is willing to trade at all — before this, a client had no way to learn that except by hardcoding it out of band. A station exposes its own catalog of tradable classes, fungible and unique alike, for anyone to read, the same ungated "read is open" treatment Browsing gets just above: each entry names its `class`, a display `name`, an optional `thumbnail`, its `fungible` flag (so a client can tell which shape of `offer`/`want` applies before composing one), and its `tradeScope` (§5) — filtered only to `tradeScope !== "bound"`, the one condition every presented asset must already satisfy to be traded at all, so nothing offered here could fail that check later. This is deliberately scoped to a station's own catalog, describing only what that one domain itself is willing to trade. A client reading a *different* domain's station catalog the same way learns what that other station trades; presenting a balance issued by neither station to either one still fails the trusted-peer check above unless the two domains involved have each listed the other, which this read alone never establishes — this is for discovering what a station trades, not a substitute for knowing whether that station's own operator and a given balance's issuer actually trust each other.

**Claiming.** A visitor fulfills one specific listing by presenting their own signed intent (mirroring the listing's `want` as their own `offer` and vice versa, naming the poster's public key in `counterparty`), their own presented asset (a balance or a unique instance, whichever their side of the trade actually is), and their own Trading Station membership, alongside the target listing's id. The station verifies all three the same way it verified the original posting, confirms the named listing is still open and unexpired, confirms the claimant's intent truly mirrors it, and only then settles both sides, in order: whichever side is foreign-issued is locked (both sides, if both are) *before* either side mutates anything, then settled — the foreign side via its own issuer's relay, bundling the counterparty's output in for mail delivery when that side's own original owner isn't live for this call (Delivery, below) — and whichever side is locally issued settles the same way it always has, a fresh balance credential `supersedes`-ing what its owner held before (§5.4) for a fungible side, or a transfer of the actual presented instance for a unique one, preserving whatever per-instance state it already carried rather than minting a fresh substitute. Both sides settle or neither does: a lock that fails stops the claim before anything is spent, and a lock that succeeds but is never followed by a settle just expires on its own (above) — a station that only ever received the original posting, with no claim arriving before it expires, holds an unmatched listing that lapses and changes nothing; there's no partial-trade state visible outside the station. A claim against a listing that's already gone (claimed by someone else first, expired, or withdrawn) fails cleanly; nothing about presenting a stale claim can ever double-settle a listing that's already resolved.

**Canceling.** A poster may withdraw their own still-open listing before it's claimed, by presenting a small signed statement — *"withdraw listing `id`"* — proof-checked the same way any other signed action in this spec is, and accepted only when the signing key matches the listing's own poster. A station MUST reject a cancel naming a listing it didn't post, or one already claimed; there's nothing left to withdraw from a listing that's already settled.

**Delivery** to a poster who isn't present at the moment their listing is claimed reuses two mechanisms this spec already defines, unmodified: when the poster gave up a fungible balance, their **remainder** credential `supersedes` the balance they staked, so it's delivered the ordinary way any reissue or split remainder already is (§5.1.1, §11's asset-update channel) the next time their client asks about the (still-held, not-yet-superseded) old id — a poster who gave up a unique instead has no remainder at all, the same as any other whole-unit transfer (§5.2), since there's nothing left of theirs for a new credential to supersede. The **received** credential — of a class (or, for a unique asset, a specific instance) the poster may never have held before, so there's no old id for it to supersede — rides along as a mail attachment (§11's gift-attachment mechanism) addressed to that same old id (the fungible remainder's, or, for a poster who gave up a unique, the now-transferred asset's own former id), claimed the same explicit way any other mail gift is. Nothing new is required on the receiving end for either path; both already exist for other reasons. A visitor who claims a listing is, by definition, present for that call, so their own side of the settlement applies directly — no mail round-trip needed for the claimant, only for the poster.

**The trust surface, stated plainly.** A visitor is trusting the station for the time a listing sits open plus the moment it clears — not with custody of their wallet, not indefinitely, only with correctly holding, matching, and settling this one exchange. That's a much narrower thing to trust than a whole platform, and it's the same trust a person already extends to a real-world market operator or exchange desk. Nothing stops many independent stations from existing — no protocol field designates one as canonical, the same anti-monopoly shape as the discovery directory (§3.3) and reputation feeds (§8).

**Currency conversion.** Everything above settles a trade between two VISITORS; a domain may separately offer to convert one of its own fungible classes into another of its own fungible classes directly, with no counterparty, no listing, and no Trading Station membership involved at all — the domain itself is always the other side, so this settles synchronously in one call the same way a split (§5.4) does, just minting a different class as the result instead of more of the same one. A domain that offers this declares an `exchangeRate` for each class it's willing to convert — how many units of that class equal one unit of whichever single class the domain designates its base currency — surfaced as part of the same catalog a client already reads for discovery (the paragraph above): a class with no declared rate simply isn't offered for conversion. Designating a base currency is a per-domain choice, not a protocol-level constant — nothing requires it to be called "gold," or to be the same class from one domain to the next — and it carries no special settlement authority of its own: the rate arithmetic is symmetric between any two rated classes regardless of which one is designated, so a domain offering it can support any-to-any conversion among its own classes, not only pairs that include the base currency. A visitor spends part or all of a held balance of one class and receives the other, at whatever quantity the domain's own declared rates produce; a domain MAY round down to the nearest whole unit (every quantity in this spec is a positive integer) and refuse a spend too small to produce even one unit of the result, rather than settle a fractional or zero-quantity outcome. This is a convenience a domain chooses to offer, not a market — it sets its own rates unilaterally, the same authority it already has to set what a class carries at all (§5), and nothing here claims to discover a fair price the way the trading mechanism above does between two independent visitors.

**A further-out option, not v1.** A visitor who doesn't want to trust even the station for the time a listing sits open can use a hash-time-locked exchange — the same cryptographic technique cross-chain crypto trades use for a fully trustless atomic swap, built from plain public-key primitives, no blockchain required. It's real and it's more machinery than a first version needs; noted here as the honest upgrade path rather than specified now.

## 8. Moderation and reputation

Domain sovereignty (§10) rules out a central authority deciding which worlds are acceptable — that would recreate exactly the platform gatekeeper this approach exists to avoid. But "no central authority" doesn't mean "no signal." The web already runs a working pattern: Google Safe Browsing doesn't gate which sites may exist, it publishes a list of known-bad ones a browser consults and acts on independently, and email's DNS blocklists have handled abuse the same way for two decades — list and infrastructure kept separate, anyone free to run a competing list. The same shape applies here, deliberately kept outside the manifest:

- **Reputation feeds** are an ecosystem-layer service, not a protocol field. Any party can publish one — `{ "manifest": "...", "reason": "...", "reportedAt": "..." }` entries at whatever URL they choose. A domain never declares its own reputation; nothing in its manifest says "trust me," because that would be exactly as useless as it sounds coming from the domain itself.
- **Clients and directories subscribe voluntarily** and decide what to do with a hit — warn before entry, exclude from search, refuse to auto-render without confirmation. Nobody is required to consult any feed, or any feed at all.
- **Reporting** mirrors the discovery directory's submission endpoint (§3.3): a `POST /report`, reviewed by a person before it affects anything — auto-actioning raw reports would just hand out a brigading tool.

This is a mitigation, not a solution, worth saying plainly rather than marking closed: a new bad actor is unlisted until reported, competing feeds can disagree, and nothing stops a client from checking none at all. The same limit every blocklist-based system on the internet already lives with, Safe Browsing included.

## 9. Security considerations

- **Issuer key compromise** is scoped to that one domain, the same blast radius as a compromised TLS certificate — not systemic, since there's no shared registry to poison.
- **Visitor key loss** (lost device, no passkey backup) means losing access to every asset issued to that key, fungible or not, the same failure mode as losing a hardware wallet. Recovery is a client/UX problem, deliberately kept outside the protocol.
- **Replay** of a presented credential is prevented by requiring a fresh WebAuthn assertion per presentation, not by trusting a cached proof.
- **Domain takeover** inherits the same trust an attacker who gains control of a domain already has over its TLS certificate and DNS — no new attack surface beyond what domain ownership already grants. Optional domain identity pinning (§3.7) narrows this, but only for a visitor whose client already remembered the domain's key from before — an attacker who takes over the domain still can't produce a valid signature under the old key, so a returning visitor's client can notice the change even though the certificate and DNS both check out perfectly. It gives nothing to a first-time visitor, and nothing at all to a client that never chose to remember the key in the first place.
- **Revocation and reputation lists** inherit the same domain-ownership trust root as everything else (they're hosted at the issuer's own `.well-known` path) — no new infrastructure to compromise beyond the domain itself.
- **A misbehaving trading station** (§7) can, at worst, refuse to settle a trade or stall it until the intent expires — it never gains custody of a wallet and can't produce a valid transfer for anything it wasn't handed a matched, signed intent for. Its blast radius is bounded to trades routed through it, not to anyone's holdings generally. Holding an open listing pending a claim doesn't widen this: the presented balance sits in the station's own pending-listing store exactly as submitted, not moved or escrowed anywhere, and the worst a station can do with it is the same as above — settle it, or don't. Making listings publicly browsable discloses nothing beyond what posting one already reveals by design — a listing's offer, want, and poster public key are exactly what a prospective buyer needs to decide, and a poster who doesn't want that visible simply doesn't post it.
- **Why cross-domain trading (§7) needs a trusted-peer allowlist, not just atomicity.** An issuer's minting authority is unlimited and unaudited by anyone outside its own domain — the same fact "Issuer key compromise" above already treats as scoped and low-risk, because nothing forces a visitor to hold, or a station to accept, a class from a domain they haven't chosen to trust. An open, anonymous listing changes that calculus: it's built so neither party needs to already know or vet the other, which is exactly the setting where a dishonest domain can mint unlimited fake value and let a station's own matching mechanism unload it, at scale, on visitors who extended no trust to that domain at all — a materially worse exposure than an issuer defrauding only the visitors who already chose to hold its credentials. A two-phase lock/commit that guarantees all-or-nothing settlement across two domains, by itself, does nothing to address this: it makes a fraudulent trade settle *correctly*, not *safely* — atomic theft is still theft. §7's trusted-peer allowlist is the actual mitigation, checked before any lock is even attempted: a foreign balance is never accepted into a listing or a claim unless the station's own operator chose to trust that balance's issuer, and a foreign relay request is never honored against a domain's own credentials unless that domain's own operator chose to trust the relaying station — the same opted-in-both-ways posture already required of a *visitor* joining a Post Office or a Trading Station, now required of a *domain* before it will trade with another one at all. A domain that lists no peers trades exactly as it did under the one-version-earlier rule that restricted a station to its own catalog outright; §5.6's direct transfer remains available for a visitor who wants to move a specific asset to a specific cross-domain counterparty with no allowlist, no station, and no lock/commit involved at all.
- **Key-anchored world impersonation.** A key-anchored world (§3.6) has no domain-ownership backstop — its signature proves the content is unaltered and genuinely came from whoever holds that key, nothing more. A bad actor can generate a key and a plausible-sounding name exactly as easily as a good actor can. This is why §3.6.1 requires an explicit, hard-to-miss disclosure rather than treating a key-anchored world as equivalent to a domain-anchored one; reputation feeds (§8) and directory listings (§3.3) are the only mitigation, and both are voluntary and incomplete for the same reasons already noted in §8.
- **A key-anchored world's identity has no recovery path.** Losing the private key behind an `identityKey` (§3.6) is unrecoverable in the same way losing a visitor's passkey is (above) — except a domain-anchored world can at least fall back on proving continuity through DNS if it ever needs to, and a key-anchored world has nothing else to reach for. The only mitigation is the same key-history mechanism §5.3 already defines for issuers: a new identity claiming continuity with an old one has to say so explicitly, and a client only believes that claim if it can actually verify it.
- **Plain HTTP silently strips more from a domain-anchored world than from a key-anchored one.** §3.6.1 covers the client-behavior requirement; stated here as a security fact rather than a client obligation: a domain-anchored manifest's entire trust basis is TLS, so serving it over plain HTTP doesn't degrade that trust, it erases it completely — worse than an honestly-disclosed key-anchored world, which still has its own signature intact regardless of transport. A deployment or client that tolerates plain HTTP for a domain-anchored world isn't degrading gracefully; it has silently become unverifiable.
- **Bridging real money into a tradeable fungible asset** is a domain's own choice (§10) — how a domain accepts payment is entirely its business, the same as any checkout flow — but it isn't a low-risk one once that asset can also move to a different visitor through a trading station (§7). A fungible asset purchasable with real currency and tradeable across independently-run domains is structurally close to what regulators mean by convertible virtual currency, the pattern that has previously pulled virtual-world operators into money-transmission, KYC/AML, and licensing questions they didn't anticipate (Second Life's Linden Dollars being the clearest precedent). This spec has no mechanism to address that, and nothing here is legal advice — a domain considering it should get real counsel in its own jurisdiction before building it, not spec guidance.

## 10. What belongs to the domain vs. the protocol

**The protocol carries what needs to survive leaving the domain.** Identity has to survive because it's the same visitor everywhere. Ownership — of an asset, and how much of a fungible one — has to survive because it's only portable if a domain that didn't issue it can still verify it. Discoverability and categorization have to be legible to a client or directory that's never seen this domain before. That's the whole list: identity, ownership, and the minimum vocabulary a stranger needs to find and understand a space before entering.

**Everything that only matters inside one domain stays inside it.** Who can build where, land parcels and their records, what a plot is worth, whether a visitor counts as a "resident," combat balance, quest logic, in-world chat moderation — none of it crosses a portal, so none of it belongs in a cross-domain spec, for the same reason HTTP doesn't standardize a website's login system. `profile.capabilities` advertises that a world *has* a building or combat system, the way a store's window display advertises what's inside; it is not the permission system itself, and this spec has no opinion on how a domain implements one. How an asset is *earned* — farmed, mined, grown, quested for — is the same kind of domain-local rule combat balance is; the protocol only cares what happens once it's been earned and needs to travel.

The one place this got genuinely subtle is §5.2: item loss during PvP looks like a domain-side gameplay rule, but the actual *transfer of ownership* has to be protocol-level, because ownership is one of the things that survives leaving the domain. §7 hit the same subtlety from a different angle — a trade looks like it should be entirely up to whichever world hosts the trading station, but settlement has to be protocol-level for the same reason. The resolution in both cases is the same shape: the world (or station) referees the event, but only a signature from whoever actually holds the authority — the owner's key for a transfer, the matched pair of owner-signed intents for a trade — can make it valid anywhere else. When a new domain-side idea shows up, run it through this test: does it need to be legible or valid outside the domain that created it? If yes, it's a schema addition. If no, it's the domain's own backend, and the spec should say nothing about it.

## 11. Mail

A domain can reach a visitor after they've left, and two visitors can reach each other, without either one needing a persistent connection or a shared account system — the same "no session to hand off" principle §6 step 4 already applies to presenting a credential, applied here to a message instead. Two distinct mechanisms share one wallet-side transport: a client that holds any credential from a domain periodically asks that domain, over one endpoint, "anything for what I'm holding?" — §11.1 is a domain speaking to whoever holds its own credentials; §11.3 is two visitors speaking to each other, with a domain only ever relaying, never authoring.

A message's shape is the same regardless of which mechanism produced it — `{id, credentialId, subject, body, sentAt, signature}`, optionally carrying `attachedAsset` (§11.2) or `from` (§11.3 only) — signed by the relaying domain's own key exactly the way an asset credential is (§5), and a client MUST independently re-verify that signature against the domain's currently published key (the same `.well-known/atlas-key.json` check §5 step 1 already requires) before trusting or displaying anything a mail check returns. This endpoint being reachable by anyone doesn't make its response any more self-certifying than any other network response — the signature is what does that work, same as everywhere else in this spec.

How often a client checks is deliberately unspecified — a periodic interval, a manual "check now," or both, entirely a client's own choice, the same latitude §5.1.1 already leaves for how often a wallet re-verifies a held credential's reissue status.

### 11.1 Domain-to-subscriber mail

A domain messages whoever holds one of its own credentials — most simply, whoever holds a dedicated administrative credential minted for exactly this purpose (`class: "atlas.membership"` in the reference implementation's catalog), requested by a visitor explicitly ("subscribing") the same way any other asset credential is requested (§5), but nothing in this section requires that specific class: a domain may equally mail against the `credentialId` of an ordinary item or resource balance a visitor already holds, since addressing is by credential id, not by a reserved class.

A message here is addressed to one specific `credentialId`, not to a public key directly — a domain names *which credential* it's mailing, and a client checks by handing back the set of credential ids it currently holds from that domain (`POST` to the domain's mail-check endpoint with that set), receiving back only the messages addressed to ids in it. This scoping is deliberate: it lets a domain reach its subscribers without any generic "send a message to any visitor" channel existing at all, and without a domain ever needing to know a visitor's public key independent of a credential it already issued them.

Sending is entirely the issuing domain's own affair — authenticated as the domain operator, not as any visitor, since only the domain that issued a `credentialId` has any business mailing against it. This spec takes no position on how a domain authenticates its own operator for this; it's exactly the kind of domain-local administrative concern §10 already excludes.

### 11.2 Attached gifts

A domain-to-subscriber message (§11.1) MAY carry `attachedAsset`: a complete, independently valid signed asset credential (§5), minted at send time and addressed (`owner.publicKey`) to a specific visitor. This is a second, explicit path onto a wallet, deliberately distinct from ordinary issuance (§5 step 3, request-then-mint) and from reissue (§5.1.1, silently adopted) in the one property that matters here: **a conforming client MUST NOT auto-adopt an attached gift into a wallet on arrival.** Where a reissue's replacement credential is adopted automatically because it's *replacing* something the wallet already held and already trusted, a gift is new — the entire reason this is a separate mechanism instead of a plain resend of an existing credential shape is that accepting property from a stranger, even a verified one, is a decision the recipient's client must surface as one, not fold into the same silent path a routine mail check already runs. A client presents an unclaimed gift distinctly from an ordinary message and requires an explicit claim action; only then is the attached credential verified (the same four-step check §5 step 1 already defines, since a gift's validity is no more automatic than any other credential's) and added to the wallet.

### 11.3 Post Office — user-to-user mail

Two visitors mail each other, addressed by public key, through a domain both of them have separately obtained a dedicated membership credential from (`class: "atlas.postoffice.membership"` in the reference implementation). Holding that credential at a domain is what makes it that visitor's mail relay: **membership is symmetric** — the same credential is both what lets a visitor send through that domain and what makes them reachable there, not one or the other. A domain relaying a message it received checks three things, in order, and a conforming implementation MUST check them in this order because each is meaningless without the one before it:

1. **Sender authentication.** The send request carries a payload (`{to: {publicKey}, subject, body}`) and a proof envelope over it (§6.2) — `signerRole: "webauthn"` or `"raw-ecdsa"`, either legitimate per §6.2's rule. Once verified, the envelope's `publicKey` *is* the sender's identity for the rest of this exchange; no separate `from` field in the signed payload is needed or trusted, the same reasoning a trade intent's own signer identity already relies on (§7).
2. **Sender membership.** The authenticated sender must hold a live (unrevoked) Post Office membership credential at *this* domain. This is what makes "send through this Post Office" mean something — it's not an open relay for anyone with a wallet, only for visitors this domain has already vouched for by issuing them its own credential.
3. **Recipient membership and consent.** `payload.to.publicKey` must likewise hold a live membership at this same domain — both parties belong to the *same* Post Office, not merely *a* Post Office each, UNLESS this domain is relaying on to the recipient's own home domain instead (§11.4), in which case this step is run by that home domain rather than skipped. A member may additionally narrow who reaches them beyond bare membership, self-service, on their own membership credential's roster entry: a **block list** naming specific senders' public keys (always wins), or a **friends-only mode** admitting only public keys in a snapshot the member explicitly submitted (not a live sync of any client-side friends list — a deliberate one-time disclosure, current only as of when it was last saved). A rejection from either the missing-membership case or a consent rule MUST read identically to the sender — a domain must not let a sender distinguish "not a member here" from "a member, but blocking you" from "a member, but friends-only and you're not on the list," since any distinguishable response leaks information about the recipient's preferences to a stranger who hasn't earned it.

Once all three hold, the domain relays the message exactly as §11.1 already delivers any other mail — addressed by the recipient's own membership `credentialId`, so the existing check-by-held-credential-ids mechanism picks it up with no separate transport. The one addition is `from`: the relaying domain, which already knows the sender's authenticated public key from step 1, stamps `{publicKey}` (and a registered handle, below, if the sender has one) onto the outgoing message so the recipient's client can show who a message is actually from, distinct from `attachedAsset`'s claim in §11.2, since the *identity of the sender is asserted by the relaying domain, not self-declared by the sender* — a client trusts it exactly as much as it trusts the rest of a signed mail message, no more.

**Handle addressing.** A member may register a short, unique-per-domain handle on their own membership (format- and profanity-validated by the domain, independent of any client-side check, since a modified client could skip one) instead of handing out their raw public key to correspond with. A registered handle is addressed as **`handle#domain`** — deliberately `#`, not `@`: an `@`-joined address reads as an email address and would misrepresent what this is (no inbox provider, no password recovery, nothing resembling SMTP underneath it), where `#` reads closer to what it actually is, a short tag scoped to one domain. Resolving a handle to a public key requires no authentication — knowing a handle someone has already told you is exactly as much "proof of anything" as already knowing their raw public key would be, so gating the lookup would add friction without adding any actual protection. A handle's uniqueness is scoped to the one domain it's registered at, matched case-insensitively, and is a convenience layer on top of the public-key addressing above, not a replacement for it — every check in this section still runs against the resolved public key, exactly as if it had been pasted in raw. Two members never hold the same handle at one domain, including while one of them is suspended (the suspension can be lifted, and the name must still be theirs alone then); the check and the write are one atomic step, so simultaneous claims produce one winner. Only a revoked membership releases its handle.

**Abuse detection.** Because every relayed message under this section is now tied to an authenticated sender's own membership credential (step 1 above), a domain can track sending volume per member and flag unusually bursty senders for a human operator's attention without needing any new identity concept to hang that tracking on. Flagging is informational only — it never blocks a send by itself — and is expected to be threshold-and-window based (a count exceeding some rate within some recent window) and self-clearing as a burst ages out of the window, rather than a manual, persistent moderation state. The actual remedy for a member a domain decides to cut off is the existing revocation mechanism (§5.3): revoking a Post Office membership credential removes that visitor from step 2 and step 3 simultaneously, since both checks query the same live-membership fact.

### 11.4 Domain-to-domain federation

`handle#domain` addressing (above) names a domain for a reason beyond display: it says where the recipient actually lives. Without this section, that naming was aspirational — §11.3 step 3 required both sender and recipient to hold membership at the *same* domain, so a handle naming any other domain resolved (§11.3, handle addressing is unauthenticated lookup, already cross-domain-capable) but could never actually be reached. This section closes that gap: a domain that cannot deliver a message locally because the recipient belongs elsewhere may relay it to the recipient's own home domain instead of rejecting it.

Two domains now speak to each other directly over one new endpoint, `/atlas/postoffice/relay`, and a conforming implementation MUST perform the following checks in order:

1. **Sender authentication and sender membership.** Unchanged from §11.3 steps 1-2, run by the domain the sender actually submits to (the *relaying domain*) exactly as for any other send. This is what preserves §11.3's "not an open relay for anyone with a wallet" guarantee under federation: a domain still only ever relays messages from its own vouched-for members, whether the recipient turns out to be local or reached through this section.
2. **Relay dispatch.** If `payload.to` names a domain other than the relaying domain itself, the relaying domain does not attempt local delivery. It instead makes its own outbound request to the named domain's (the *home domain's*) `/atlas/postoffice/relay` endpoint, carrying the sender's original signed payload and proof UNCHANGED — so the home domain can independently re-run step 1 itself, exactly as if the sender had submitted directly to it — plus a new attestation of its own, `{relayingDomain, relayingDomainHandle}`, signed with the relaying domain's OWN key: the same key its `.well-known/atlas-key.json` publishes and every asset credential is already checked against (§5 step 1). This attestation is what stands in, across the wire, for step 2's membership check — proof that some domain other than the sender's own has already vouched for them, since the home domain has no way to see the relaying domain's membership roster directly.
3. **Relaying-domain authentication.** The home domain fetches the relaying domain's `.well-known/atlas-key.json` and verifies the attestation's signature against it — the same cross-domain trust bootstrap §5 step 1 already relies on for any issuer's key, requiring no new discovery mechanism, since a domain name is already directly reachable by design. A relaying domain can sign its own attestation but cannot forge another domain's; an attestation that doesn't verify, or that names a relaying domain the home domain has chosen not to accept relays from (see below), MUST be rejected before proceeding.
4. **Recipient membership and consent.** Unchanged from §11.3 step 3, run by the home domain using the ORIGINAL sender's public key (carried in the relayed proof, not the relaying domain's own identity) for any block-list or friends-only check. A trusted relaying domain vouching for its own member does not, and must not, bypass the recipient's personal consent settings.

Once all four hold, the home domain relays the message exactly as §11.3 already does for a local send, with one addition to `from`: **`homeDomain`**, naming the relaying domain, alongside the existing `publicKey`/`handle`. Without it, a client has no way to render the sender's real address (`handle#relayingDomain`) and could misattribute a relayed message to whichever domain happened to deliver it rather than the domain that actually vouched for the sender.

**Federation is open by default, not opt-in.** A domain need not pre-register with, or be approved by, any other domain before relaying to or receiving from it — matching this spec's existing posture that any domain publishing a valid `atlas-key.json` is a legitimate participant (§5 step 1), the same assumption that already lets a visitor portal between domains with no registration step anywhere in this protocol. This is a real, deliberately-accepted abuse surface: a home domain has no a priori reason to trust an arbitrary relaying domain's judgment about its own membership beyond the cryptographic fact that an attestation really came from the domain it claims to. A conforming implementation SHOULD let an operator maintain their own list of relaying domains whose attestations it will no longer accept (checked in step 3 above) — a purely local, unilateral decision each home domain makes about its own inbound relay traffic, the same category of domain-local administrative concern §10 already excludes from this spec's scope, not a negotiated or protocol-visible federation-membership state between domains.

Trading (§7) is explicitly out of scope for this section, and that's no longer the same as saying it has no cross-domain mechanism at all — v1.29 gives it one, but a deliberately separate one, not an extension of federation. This section's relay authenticates a *message's sender*, vouched for by whichever domain relayed it; §7's `/atlas/trade/relay-lock`/`relay-settle` authenticate a *station* asking an issuer to mutate its own credential, which is a materially different trust question with its own gate (the trusted-peer allowlist, §7, §9) — folding one into the other would blur exactly the distinction that gate exists to draw. A Trading Station's pending-listing store remains a separate mechanism from mail's transport entirely; a visitor moving an asset to a specific counterparty on another domain, with no station and no allowlist involved, still uses §5.6's direct transfer, which needs no federation support of its own either way.

## 12. Calendar

A domain, and independently any one of its worlds, can publish a schedule of events, activities, or anything else worth putting a date on — opted into via the `calendar` manifest field (§3): `calendar: true` at the manifest's top level for a domain-wide calendar, and/or `calendar: true` on any individual world's own entry for that world's separate calendar. A domain with `calendar: true` and three worlds where only one also sets `calendar: true` publishes exactly two calendars: the domain-wide one and that one world's — the other two worlds have none. This is why §12 exists as a schema addition at all rather than being left to each domain's own backend the way most domain-local scheduling would be under §10's test: a visitor standing inside a domain wants to see what's scheduled there, and a visitor elsewhere wants to check a *different* domain's calendar without entering it — both cases require the schedule to be legible to a client that isn't the domain's own backend, which is exactly §10's line for "schema addition" rather than "the domain's own business."

Calendars carry no signature and require none. A client's trust boundary here is the same plain HTTPS fetch it already extends to the manifest itself and to §7's catalog endpoint — nothing about a public schedule of events needs a stronger guarantee than "this is really what `{domain}` is currently serving at this URL," and TLS already provides that.

An event is `{id, title, dateTime, endDateTime, notes}`: `id` a domain-assigned identifier unique within that one calendar, `title` and `dateTime` (ISO 8601) required, `endDateTime` (ISO 8601, or absent/`null` for a point-in-time event) and `notes` both optional. Nothing here requires an event to carry a location, a capacity, an RSVP mechanism, or anything else a domain might reasonably want for its own scheduling UI — same as `profile.genre` being free text elsewhere in this spec, this section standardizes only what a stranger's client needs to render a schedule of "what, and when," not what a domain's own backend uses to manage it.

### 12.1 Fetching a calendar

`GET /atlas/calendar`, optionally `?world={worldId}`:

- No `world` parameter — returns the domain's own domain-wide calendar. Meaningful only when the manifest's top-level `calendar` is `true`; a domain that never opted in returns an empty `events` array rather than an error, the same "nothing to report, not a failure" posture `GET /atlas/trade/listings` already takes for a station with no open listings.
- `world={worldId}` — returns that one world's own calendar. Meaningful only when that world's own `calendar` is `true` in the manifest; naming a world that hasn't opted in, or doesn't exist, likewise returns an empty `events` array rather than an error, for the same reason.

Response: `{ "domain": "...", "worldId": null, "events": [ { "id": "...", "title": "...", "dateTime": "...", "endDateTime": null, "notes": "..." } ] }`, `worldId` echoing the request (`null` for the domain-wide calendar, the requested world's id otherwise) and `events` sorted soonest-first by `dateTime`, the same ordering `AtlasWallet.getCalendarEvents()` already guarantees for a wallet's own local reminders. This is a read anyone may make — no membership, no credential, no identity — the same "already public the moment it's published" reasoning §7's catalog endpoint gives for its own unauthenticated read.

### 12.2 Authoring

`POST /atlas/calendar` adds, updates, or removes one event on one of a domain's calendars — a real, protocol-level write endpoint, not left to each domain's own ad hoc admin tooling, because §12.1's read contract only means something if there's a standard way to have put something there in the first place. Authenticated as the domain operator, not as any visitor, following §11.1's exact precedent for domain-to-subscriber mail: this spec takes no position on how a domain authenticates its own operator for this call, only on the shape of the request and of what a subsequent §12.1 read then returns.

Request body: `{ "action": "add" | "update" | "remove", "worldId": null | "...", "event": { ... } }` for `add`/`update` (`event` the shape from §12, `id` optional on `add` — the domain assigns one if absent, required and identifying which event to change on `update`), or `{ "action": "remove", "worldId": null | "...", "id": "..." }` for `remove`. `worldId: null` (or the field's absence) addresses the domain-wide calendar; naming a world addresses that world's own, and requires that world to itself have `calendar: true` in the manifest, same as §12.1's read side.

## 13. Email-delivered bearer credentials

Every mechanism through §5 and §7 assumes the recipient already has a wallet — a public key to mint something to, a client able to hold and re-present a signed credential. A domain often wants to serve someone who doesn't: an event ticket bought by a stranger who will never install anything, a coupon a customer should be able to forward to a friend with no app involved at all. This section defines an opt-in way for a domain to hand a bearer-instrument credential to someone with nothing but an email address, and for that credential to be held, transferred, and redeemed entirely through an ordinary inbox — purchase through redemption, with a wallet never entering the picture.

**Why this doesn't need a new identity primitive.** Two obvious-looking shortcuts both fail for the same underlying reason. Deriving a keypair deterministically from the address itself (`hash(email) → keypair`) has no real secret behind it beyond the issuer's own master seed — worse than an ordinary custodial account, and unrotatable if that seed ever leaks. A genuine identity-based-encryption scheme fixes the rotation problem but introduces the thing this spec has otherwise never needed: a permanent custodial chokepoint whose compromise would affect every email-addressed credential a domain has ever issued, not just one. This section needs neither. It's the identical bearer rule this reference implementation's own self-serve routes and §5.5's World Drops already run on — whoever currently holds the one valid credential may act on it — carried over a different transport (ordinary email) instead of a signed HTTP call. No master secret, no derived keys, no custodial signer; the issuer's own existing signing key (§5.3) is all that's required.

### 13.1 Manifest opt-in and eligibility

A domain opts in with a new top-level manifest field (§3), sibling to `calendar` (§12) rather than a `policy.*` field — this is a mailbox the domain itself operates, not a per-world concern, so it does not follow §3.4.1's domain-default/world-override shape any more than `calendar` does, for the mirror-image reason: there is exactly one of these per domain, never a world-specific override to fall back from in the first place.

```json
{
  "emailTickets": { "intakeAddress": "tickets@example.com" }
}
```

Presence of `emailTickets` IS the opt-in; its absence means a domain supports none of what follows. `intakeAddress` names the mailbox this domain monitors for inbound transfers (§13.3) — provisioning and authenticating that mailbox is the domain's own operational concern (§10), out of scope below.

Eligibility reuses the identical two conditions §5.6's direct transfer and §5.7's redemption already share, for the same reasons: `asset.fungible === false` (there is no quantity to negotiate over email) and `asset.tradeScope !== "bound"` (a relationship credential was never meant to leave its owner's hands at all, §5's "Three flags, one discipline"). A domain may offer this delivery path for any class meeting both, the same way any class becomes purchasable (§5.8) or self-expiring (§5.10) by opting in at the catalog level rather than needing a new credential shape of its own.

**Entering the system.** A ticket enters this mechanism the same way §5.6's direct transfer moves a credential between two wallets — current owner, full credential, signed intent — except the intent names an email address instead of a recipient's public key: `POST /atlas/asset/transfer-to-email`, body `{credential, recipientEmail, intent: {payload: {credentialId, recipientEmail, action: "transfer-to-email"}, proof}}`. Verification is §5.6's own, unchanged (signature checks out, intent.proof's key matches credential.owner.publicKey, this section's own eligibility above), gated additionally on this domain actually having SMTP delivery configured right now — rejected outright if it doesn't, the same as any other manifest-gated capability in this spec being refused when the capability it advertises isn't really there. Once authorized, the presented credential is revoked (§5.3, reason `"email-transferred"` — the same code §13.3's own forwards use below, since both tell an identical story: this credential left here because it became, or moved on as, an email-delivered bearer credential) and a fresh one minted exactly as §5.6 already does for a wallet-to-wallet move, with one necessary difference: `owner.publicKey` on the freshly minted credential is a keypair the issuer generates and immediately discards, never handed to anyone — there is no wallet on the receiving end for it to belong to, and nothing in §13.3's forward-to-transfer or §13.4's redemption ever checks this field's signature again. The field exists only so the credential keeps the exact same `domain-atlas-asset/1.0` shape §5 already defines everywhere else; actual authority over an email-delivered credential is bearer-only from this point on — possession of the attachment (§13.3) or the short token (§13.4) — never this key. The same mint-before-revoke ordering §5.4.1, §5.12, and §13.3 below all already use applies here too: the fresh credential is minted and the outbound send attempted before the presented one is revoked, so a send the mail server never actually accepts leaves the sender exactly as they were.

### 13.2 Outbound delivery

Sent as a real MIME attachment carrying the credential's own canonical JSON (§5) — never as body text, which no two mail clients forward byte-for-byte alike — plus an optional QR image encoding a short, opaque bearer token minted alongside the credential and bound to it, not the credential itself. The split is deliberate: the attachment is what actually lets the credential be held and forwarded (§13.3); the QR exists purely as a compact presentation form for the redemption step (§13.4), where encoding a fully offline-verifiable credential would buy nothing anyway — redemption already requires a round trip to the issuer regardless (below), so there is no benefit to a QR large enough to hold the whole thing, only the cost of making one that's harder to scan.

### 13.3 Transfer by forwarding

A ticket moves exactly the way its holder would already expect an email attachment to move: forward it, CC the new recipient, done. No wallet, no claim step, no reply required of anyone.

The new recipient is identified by being CC'd on the forward to the domain's own `intakeAddress` — never by parsing the forward's body text, which varies unpredictably across mail clients' own quoting conventions. The system locates the credential being transferred by finding its own original JSON attachment, still present in the forward (every mail client preserves attachments on forward by default); there is no sender authentication beyond that, deliberately — this is a bearer instrument, and holding the attachment is the entire proof of authority to move it. What makes a credential a bearer ticket is the issuer's own record, not its signature: a signed credential is a public claim anyone can copy (§13.5's bearer registry explains why), so the issuer lists every id it mints as an email ticket (§13.1, a bounce reissue, or a forward) in the same registry, and a forward is acted on only if the attached credential's id is listed. A forward of anything else, such as a copy of an ordinary wallet credential, is ignored without a reply, since answering would tell a stranger which ids the issuer has issued as tickets. Taking the registry entry is also what makes the step atomic: a second forward of the same ticket finds no entry. A ticket minted before a domain adopted this rule is not in the registry and cannot be forwarded; the holder can ask the issuer to reissue it.

**Instant reissue, no claim step.** On receipt, the system immediately revokes the forwarded credential and mints a fresh one addressed to the CC'd recipient — no pending state, no reply-to-claim, nothing resembling §11.2's attached-gift claim step, because there is no wallet on the receiving end to present a claim UI in the first place. This is still atomic under the hood: find, revoke, and mint happen as one unbroken step, the same "removal is the reservation" property §5.5's Claim and §5.12's Clawback already rely on, so a second, concurrent forward of the identical ticket simply finds nothing left to revoke.

**Delivery check before finalizing.** The new credential is minted and the outbound send to the CC'd address attempted before the old one is revoked — the same mint-first-revoke-second crash-safety ordering §5.4.1 and §5.12 already use — and the old credential's revoke only finalizes once that outbound send is positively accepted by the recipient's own mail server, not merely attempted. A typo'd or dead address is caught here without ever requiring a human-facing claim step: nothing is finalized against an address that never actually accepted the message.

**Ongoing bounce monitoring.** Acceptance at send time isn't the end of the story — a downstream bounce can still arrive after the transfer has already finalized. The domain's own mailbox keeps watching for these, correlating a bounce back to the specific send that produced it via VERP (a unique per-send envelope Return-Path, e.g. `bounce+{ticketId}@example.com`) rather than parsing bounce bodies, which vary too much across mail servers to parse reliably. A correlated bounce revokes the bounced credential and reissues it back to whichever address actually sent the original forward, with a plain-language explanation of why ("this ticket was returned to you because delivery to the address you sent it to failed"). Every transfer this section defines resolves to exactly one of two states — the new address holds it, or it's back with the sender and told why — never a silent limbo. The one honest limit this can't close: silent spam-foldering gives no bounce at all, so it gives this mechanism nothing to react to either.

**Double-addressing, denied, never named.** A ticket can end up pointed at two recipients two different ways, and both are refused rather than silently resolved: a single forward CC'ing more than one address is rejected by validation before anything is sent at all ("this ticket was forwarded to more than one recipient; transfer denied"); two separate forwards racing each other, each naming a different single CC, are resolved by the same atomicity already described above — one wins, and the loser now also gets an explanatory reply instead of simply failing silently. Both replies, and the bounce-reversal notice above, follow the identical rule: never name the address the ticket actually went to. A sender could otherwise use the denial itself as an oracle, forwarding to a throwaway address they control purely to learn whether a second, real destination exists — stating only that the ticket was already transferred, with a timestamp, gives nothing away.

### 13.4 Redemption ("used")

A wallet-free recipient can't produce §5.6's or §5.7's own holder signature at redemption time either, so this needs a different endpoint from `/atlas/asset/redeem` — one built on this reference implementation's own `/atlas/demo/*` self-serve bearer pattern instead, which verifies the *issuer's* signature on the presented credential, never a presenter's: the same "whoever holds the valid thing may act on it" rule this entire section already runs on. The short opaque token §13.2 already introduced is what a door-side scan actually submits to this endpoint — resolving the QR-encoding question §13.2 left open in favor of the token rather than the full credential, for the reason already given there: the issuer has to be reached either way, so nothing is gained by making the QR self-contained, only a harder scan.

**"Used" suspends; it doesn't revoke — not at first.** The suspend mechanism §7's own Lock step already relies on (`suspend(id, reason, expiresAt)`, reversible by `unsuspend()`, `expiresAt` optional) has, until now, had exactly one meaning for what happens once its timer runs out: the suspension lifts, and the credential goes back to being ordinarily valid — correct for §7's own use (an abandoned trade should simply unwind) and for an administrative hold pending review, but backwards for a redeemed ticket, which is not supposed to come back to life once the event it was scanned into has ended. This section is the first to need the other outcome, so `suspend()` now takes a fourth, optional argument, `onExpire: "lift" | "finalize"`, defaulting to `"lift"` — every suspension ever created before this version, and every call site that doesn't pass it explicitly, keeps today's exact behavior unchanged. A door-scan redemption suspends with `onExpire: "finalize"` and an `expiresAt` set to the event's own end time: while the event is still running, a mis-scan or a legitimate re-entry can still be reversed with the ordinary `unsuspend()`, exactly as any other suspension can be; once that deadline passes, the suspension's own expiry revokes the credential outright (§5.3, reason `"redeemed"`) instead of silently reactivating it.

Two new revocation reason codes ride alongside the existing list (§5.3): `"email-transferred"`, recorded against the old credential every time §13.3's forward-to-transfer completes; and `"redeemed"`, recorded when a `"finalize"`-suspended ticket's window closes, above — distinguished from each other, and from every other reason already in that list, for the identical reason `"fulfilled"` (§5.9) and `"clawback"` (§5.12) got their own codes rather than reusing `"issuer-request"`: a client reading the revocation list has a materially different story to tell depending on which one it finds.

**Deliberately out of scope**, per §10's own test — none of it needs to be legible to a client outside the domain that runs it: how a domain actually sends and receives mail (IMAP polling vs. an inbound-parse webhook, OAuth vs. password auth against whichever mail provider it uses), spam and abuse filtering on the intake mailbox, and rate limits on transfer or redemption attempts. This section specifies the wire format a credential travels in and the state transitions a transfer or redemption produces — exactly §10's line between a schema addition and a domain's own backend, same as everywhere else in this spec.

### 13.5 Transfer by file

§13.1 delivers a bearer credential by email. The same credential can travel as a plain file the holder saves and hands over by any channel (a chat attachment, a USB stick, a download link). Nothing about a bearer credential depends on how it arrives, so §13.5 adds the export and claim steps and leaves the credential shape alone.

**Manifest opt-in.** A domain opts in with a new top-level field, a sibling of `emailTickets` (§13.1) and `calendar` (§12) for the same reason: it is an operation the domain performs, not a per-world setting, so it does not follow §3.4.1's domain-default/world-override shape.

```json
{
  "fileTransfer": { "classes": ["atlas.wearable.ring"] }
}
```

Presence of `fileTransfer` enables exports. The optional `classes` array limits exports to those asset classes; absent, every eligible class may be exported. Eligibility is §13.1's, unchanged: `asset.fungible === false` and `asset.tradeScope !== "bound"`. A holder of a fungible balance who wants to hand over a single unit splits it first (§5.4). Only the issuing domain can export or claim its own credentials; a credential issued elsewhere is exported and claimed at its issuer.

**Export.** `POST /atlas/asset/transfer-to-file`, body `{credential, intent: {payload: {credentialId, action: "transfer-to-file"}, proof}}`, where `proof` is the current owner's signature, checked exactly as §5.6 checks a transfer. The issuer verifies the presented credential (its own signature; not revoked, suspended or expired; eligible), mints a fresh credential whose `owner.publicKey` is a key it generates and discards (§13.1), adds the new credential's id to its **bearer registry**, revokes the owner's credential with reason `"file-transferred"`, and returns the new credential as `file`. The `asset` of the new credential is identical to the old one, so `atlas.serial`, `atlas.editionSize`, `expiresAt` and every other signed property carry over unchanged; moving a file never extends an expiry or resets a serial. Two exports of the same credential at once produce exactly one file.

**The bearer registry.** A credential is public: anyone who has seen one can hold a perfect copy. "This credential is validly signed by the issuer" can therefore never be what lets a stranger take ownership, or anyone holding a copy of an ordinary wallet credential could claim it. What authorizes a claim is the issuer's own record that it minted this id as a file. An issuer lists an id in the registry when it mints a bearer credential, whether for a file or for email delivery (§13.1, §13.3), and removes it when the credential is claimed or forwarded. Because the registry is shared, a registered email ticket can also be claimed into a wallet through §13.5's claim when the domain has opted in to file transfers for its class. The registry is the issuer's private state; it is not published.

**Claim.** `POST /atlas/asset/claim-from-file`, body `{credential, intent: {payload: {credentialId, newOwnerPublicKey, action: "claim-from-file"}, proof}}`, where `proof` is signed by `newOwnerPublicKey`, so the claim proves the claimer holds the key that will own the asset. The issuer checks, in order: the intent; that it issued the credential and its signature is valid; not revoked (an already-claimed file answers `already-claimed`), not suspended, not expired; eligibility as above; and finally that the id is in the bearer registry. It then mints a credential owned by `newOwnerPublicKey` (an ordinary §5 credential, `supersedes` the file's id), commits the claim (§13.5.2), removes the registry entry and revokes the file's credential with reason `"file-claimed"`. Claims of one file are handled one at a time, and the commit is the reservation: simultaneous claims by different keys have exactly one winner and every other claimer is told `already-claimed`. If minting fails nothing has been written and the file stays claimable. A presented credential that is not in the registry, which includes every ordinary wallet credential, is refused as `not-claimable` and nothing is revoked.

The registry decision applies to claims whether or not the domain still has `fileTransfer` in its manifest: removing the field stops new exports but does not strand files already handed out.

**Status.** `GET /atlas/asset/file-status?id=<credentialId>` answers `{id, state, claimable}` with `state` one of `claimable`, `claimed`, `suspended`, `revoked` or `unknown`. It lets a client say "already claimed" before offering a claim. An id the issuer has no bearer record of, including every ordinary wallet credential, answers `unknown`.

**Consequences a client should state.** Exporting removes the asset from the exporter's wallet. Whoever holds the file first can claim it; a file sent to several people goes to whoever claims first, and a lost file is lost unless the exporter kept a copy (a client that keeps one lets the exporter claim it back, racing everyone else). A claim revokes the file's credential, so every copy of the file stops being claimable at once. "Valid" in a client's preview means the issuer's signature checks out and the credential is not revoked or suspended; it does not mean the person previewing is the only holder.

Two new revocation reason codes extend the list in §5.3: `"file-transferred"`, recorded against the exporter's old credential, and `"file-claimed"`, recorded against the file's credential once it is claimed.

#### 13.5.1 Interrupted exports

An export is several separate writes, and a reply can be lost after the issuer has finished. The issuer therefore keeps a durable **export record** per exported credential and advances it through explicit states, writing each state before moving on and never assuming the steps are atomic:

| State | On disk | Original | File |
|---|---|---|---|
| `prepared` | record written | spendable | not listed, so not claimable |
| `original-revoked` | original revoked (`"file-transferred"`) | revoked | not yet listed |
| `pending` | file listed in the bearer registry | revoked | claimable |
| `claimed`, `abandoned`, `revoked` | terminal | — | — |

The order is the safety property: the original is revoked **before** the file is listed, so at no instant are both live. The file is released to the owner only from `pending`. An issuer reconciles a record from whatever state it finds, and every step is idempotent: `prepared` with the original revoked for some other reason becomes `abandoned` (the file was never listed or released and is dropped); `prepared` otherwise revokes the original and continues; `original-revoked` lists the file if it is not already listed; `pending` reports the file claimable, or derives `claimed` / `revoked` from the revocation list, or reports a claim in progress when the registry entry has been taken but the file is not yet revoked. Reconciliation is the same code on the normal export path and on recovery.

**Recovery.** `POST /atlas/asset/recover-file-export-challenge` with `{credentialId}` returns `{challenge, expiresAt}`. It is stateless and answers identically for any id. The owner signs `{credentialId, action: "recover-file-export", challenge}` with the key that signed the export, and sends it as `intent` to `POST /atlas/asset/recover-file-export`. A challenge is bound to the credential id, signed by the issuer, valid for five minutes and accepted once; the issuer records the nonce when it is used, so a captured request cannot be replayed to obtain the file. If the signature, the challenge and the export's recorded owner key all match, the issuer reconciles the record and answers: `200 {status: "pending", file, exportId}` (the same file on every repeat), or `409` with `code` `already-claimed`, `export-abandoned`, `file-revoked`, `suspended` or `in-progress` and a compact `receipt`. An unknown id and an export by another key both answer `404 not-found` with identical bodies. Recovery never mints a credential and never lists a second file.

A second `transfer-to-file` for an already exported credential answers `409 already-exported`; the owner recovers instead.

**Receipt.** When a record reaches a terminal state the issuer drops the file and the original credential and keeps `exportId`, `originalId`, `fileId`, the owner key, the class, the outcome and its reason, the state transitions with their timestamps, and for a claim the claimed time and the claimant's new credential id.

The export store, the bearer registry and the revocation list use the same JSON shapes in every implementation (a registry with no entries is an empty object, not an empty array), so a domain can move its state files from one implementation to another mid-export and the new one finishes it.

Exports completed before an issuer supports this have no record and cannot be recovered.

**Client behaviour (recommended).** A wallet records the intended export locally before sending `transfer-to-file`, and keeps the original credential until it holds a verified file or the issuer has said the export did not happen. When a reply is lost it runs the recovery exchange above immediately and again whenever it is next opened. A `404 not-found` is believed only once the local record is a couple of minutes old, so a request still in flight is not mistaken for one that never arrived; after that the record is dropped and the original stays spendable. A returned file is accepted only if it verifies, supersedes the recorded original and names the issuer the export was sent to. `already-claimed`, `file-revoked` and `export-abandoned` settle the local record without a file and the revoked original is removed from the wallet. A client that cannot sign without a person present (a passkey) waits for the holder to ask.

#### 13.5.2 Interrupted claims

A claim is several separate writes, and the new credential would otherwise exist only in the reply. A process stopping after the registry entry was taken, or a reply lost on the way, would leave a file nobody can claim and a claimer holding nothing. The claim therefore commits before it changes the registry or the revocation list.

**Commit.** After minting, and before anything else is written, the issuer stores a claim record for the file: `claimId`, `fileId`, `mintedId`, the claimer's key (`claimantPublicKey`), the class, the minted credential, and `state: "committed"` with timestamps. From this write on the claim belongs to that key. Taking the registry entry and revoking the file come after it and are repeatable; when both are done the record becomes `claimed`. Any request that reaches the file finishes a committed claim first, whoever sent it, and an export recovery (§13.5.1) that finds the file taken but not revoked finishes it too and reports `already-claimed`.

**Retry.** A claim request for a file that has a record is answered from the record. The key that committed it receives the stored credential again, byte for byte, with no second mint. Any other key receives `409 already-claimed` with nothing about the credential. No new endpoint is needed: the claimer repeats the same request, authorized by the same signature as the first.

**Receipt.** The stored credential is kept for a replay window (30 days by default) after the claim, then dropped; the record keeps `claimId`, `fileId`, `mintedId`, the claimer's key, the outcome and the transition timestamps. A retry after that is answered `already-claimed` with a `receipt` of `claimId`, `mintedId` and `claimedAt`, for the key that claimed and for no other. `GET /atlas/asset/file-status` reports `claimed` as soon as the claim is committed.

The claim store uses the same JSON shapes in every implementation, so a domain can move its state files between implementations mid-claim.
