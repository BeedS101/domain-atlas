Buy something with a balance

A worked example of SPEC.md §5.8 (purchasing) and §5.9 (fulfillment).

A parent or organization tops up a student's spendable balance, the student spends part of it on something from a small menu, and gets a signed receipt to present at pickup. Every step below is a real call to this domain's own server — the balance and the receipts are genuine credentials, not a mockup.

What this actually demonstrates

POST /atlas/asset/purchase has no idea it's selling food — a class becomes purchasable the moment a catalog entry declares its own price, and the identical endpoint would sell an item in a spatial world's shop the same way, with no code of its own for either case. This page is one worked example of a generic mechanism, not a cafeteria-specific feature.

Step 2 — a parent (or the organization) tops up the balance

Mints spendable balance straight into the student's wallet (POST /atlas/asset/issue, merged with any existing balance via POST /atlas/asset/consolidate). A real deployment only runs this once actual payment has cleared; this demo mints it freely, the same "no real payment custody" limitation every class in this reference implementation already has.

Step 4 — collect at the counter

Each purchase above minted a receipt credential the student presents at pickup. Take one's raw JSON to the Admin Panel's "Fulfill a purchase" section — the operator confirming it's genuine and hasn't already been collected, then handing over the order (POST /atlas/asset/fulfill). "Check status" below re-reads this domain's own public revocation list, the same file anyone could fetch directly, to show whether that's happened yet.

Nothing on this page is stored in a database anywhere beyond the credentials themselves. The balance is bound to the student's own key — it can be spent, never gifted or traded away — and a receipt, once fulfilled, is revoked the same one-sided way a redeemed credential is: the operator's own signature is enough, nothing further is required from the student's side.
